## Дополнительные рекомендации

### Р10. Определить судьбу issue #25 до закрытия курса

**Проблема:** issue #25 (Performance 0.77) открыт как мониторинг, но цель
(Performance ≥ 0.9, TBT < 200 мс) не достигнута. Ночной cron будет обновлять
issue комментариями, но без плана работ по улучшению производительности issue
останется открытым неопределённо долго.

**Почему это важно:** курс требует «видимого следа» — открытый issue без
намеченного пути закрытия противоречит принципу «след = ссылка». Владелец
должен решить: (а) назначить работу по улучшению производительности (отдельная
ветка, PR, релиз), (б) закрыть issue как мониторинг (цель достигнута после
N зелёных замеров), или (в) изменить цель на реалистичную.

**Рекомендация:** до закрытия шага 6 (пункт 6.10) зафиксировать решение:
- Если (а): создать задачу в tasks.md (отдельная ветка `fix/perf-improvements`),
  оценить объём, назначить срок.
- Если (б): определить критерий закрытия (например, «3 последовательных зелёных
  замера Performance ≥ 0.85»).
- Если (в): обновить цель в issue #25 и зафиксировать причину изменения.

### Р12. Зафиксировать план работ по issue #12 (отмена брони)

**Проблема:** issue #12 имеет критерии приёмки (добавлены владельцем 2026-09-05),
но работа не начата. Это фича из плана развития (docs/development-plan.md),
которая должна демонстрировать полный цикл «issue → triage → fix → review → release».

**Почему это важно:** план развития требует «≥1 фича и ≥1 баг». Баг #10 (длинный
email) исправлен (PR #15, релиз 1.0.3). Фича #12 (отмена брони) остаётся
нереализованной — план развития выполнен частично.

**Рекомендация:** после закрытия шага 6 (пункт 6.10) начать работу по issue #12:
- Создать ветку `fix/booking-cancellation`.
- Выполнить `/oc fix` в issue #12 с критериями приёмки.
- Пройти полный цикл: PR → ревью → правки → мерж → релиз (версия 1.1.0, т.к.
  фича — minor по SemVer).
- Обновить tasks.md: добавить задачу «Фича 1: отмена брони» со ссылкой на PR.

### Р13. Определить стратегию релизов после v1.0.3

**Проблема:** после релиза 1.0.3 (фикс бага email) новых релизов нет. Issue #12

**Почему это важно:** release-please автоматически создаёт release-PR при мерже

**Рекомендация:** зафиксировать в tasks.md (раздел «Вне шагов курса» или отдельный):
- Краткосрочный план: issue #12 → релиз 1.1.0 (minor, т.к. фича).
- Среднесрочный план: issue #25 → релиз 1.1.1 (patch, если оптимизация) или
  1.2.0 (minor, если значительные изменения).
- Долгосрочный план: мониторинг производительности, возможные улучшения UX.

### Р14. Уточнить критерий закрытия issue #25 (мониторинг vs работа)

**Проблема:** issue #25 открыт с целью «Performance ≥ 0.9, TBT < 200 мс, повторный
замер». Но неясно, что считается «повторным замером»: один зелёный замер, три
последовательных, или достижение цели в течение N дней?

**Почему это важно:** без чёткого критерия issue может остаться открытым вечно
(всегда есть возможность «ещё один замер»). Это противоречит принципу «задача
закрыта только после мержа в main».

**Рекомендация:** добавить в issue #25 комментарий с критерием закрытия:
- Вариант (а): «3 последовательных ночных замера Performance ≥ 0.85 без красных
  прогонов» (мониторинг стабилен).
- Вариант (б): «Performance ≥ 0.9 в одном замере после оптимизации» (работа
  выполнена).
- Вариант (в): «Закрыть через 14 дней, если цель не достигнута, и создать новую
  задачу с реалистичной целью» (пересмотр плана).

### Р15. Добавить в tasks.md раздел «Известные ограничения»

**Проблема:** tasks.md содержит детальный реестр задач, но не фиксирует известные
ограничения процесса (например, «approve ботовых PR только в UI», «YAML pull_request
из head-ветки», «одиночный комментарий ревью иногда дублируется»).

**Почему это важно:** новые участники (или будущие сессии агента) могут столкнуться
с этими ограничениями и потратить время на их «исправление». Фиксация в reestr
экономит время и предотвращает повторные ошибки.

**Рекомендация:** добавить в tasks.md раздел «Известные ограничения» (после
«Принятые решения»):
- Approve ботовых PR (release-please, opencode-agent) — только пользователь в UI.
- YAML `pull_request` берётся из head-ветки PR, а не из base (факт 4.7b).
- Авторевью иногда оставляет два одинаковых комментария (ограничение модели, Р8).
- Ночной cron может не запуститься, если репозиторий неактивен 60 дней (GitHub
  ограничивает schedule для неактивных репо).

### Р16. Проверить актуальность пинов SHA в opencode-воркфлоу

**Проблема:** все opencode-воркфлоу используют пин `anomalyco/opencode/github@16747470f976aca3d362ad730bcd3fe82ecc2c9a`
(v1.18.29). Актуальная версия может быть новее (проверить на GitHub).

**Почему это важно:** пины на SHA — лучшая практика (безопасность, воспроизводимость),
но устаревшие версии могут не содержать исправлений багов или новых возможностей.

**Рекомендация:** перед закрытием шага 6 (пункт 6.10) проверить:
- Актуальная версия `anomalyco/opencode/github` (GitHub → Releases).
- Если есть новая версия — обновить пины во всех четырёх воркфлоу (opencode.yml,
  opencode-triage.yml, opencode-review.yml, opencode-schedule.yml).
- Протестировать на ручном dispatch schedule-воркфлоу.
- Зафиксировать в tasks.md: «пины актуальны на дату закрытия шага 6».

## Стратегические вопросы (требуют решения владельца)

### В1. Закрытие курса: когда считать проект завершённым?

Курс требует 6 шагов. Шаги 1-5 закрыты, шаг 6 подходит к концу. Но открытые
issue (#12, #25) и незакрытые задачи (5.10, 6.10, 6.11) создают неопределённость:
когда проект считается завершённым?

**Варианты:**
- (а) После закрытия 5.10/6.10/6.11 (формальное завершение курса).
- (б) После реализации issue #12 (полный цикл фичи).
- (в) После достижения цели в issue #25 (производительность ≥ 0.9).

**Рекомендация:** вариант (а) — курс завершается формально, открытые issue
остаются как «долгосрочные задачи» (не блокаторы курса).

---

### В2. Долгосрочная поддержка: кто отвечает за мониторинг?

Ночной cron (opencode-schedule.yml) запускается ежедневно. Если производительность
деградует (Performance < 0.7), кто принимает решение о работе по улучшению?

**Варианты:**
- (а) Владелец (вручную отслеживает issue #25).
- (б) Агент (автоматически создаёт задачу при N красных замерах).
- (в) Команда (еженедельное ревью открытых issue).

**Рекомендация:** вариант (а) — владелец получает уведомление от GitHub при
обновлении issue #25, решение о работе принимает вручную. Автоматизация (б)
возможна, но требует дополнительного воркфлоу (не требуется курсом).

---

### В3. Расширение функциональности: что после issue #12?

После реализации issue #12 (отмена брони) план развития будет выполнен полностью.
Что дальше?

**Варианты:**
- (а) Остановиться (курс завершён, проект — демо).
- (б) Добавить новые фичи из backlog предшественника (386).
- (в) Передать проект команде для продуктовой разработки.

**Рекомендация:** вариант (а) — курс учебный, продукт не растёт (согласно
user-story). Дальнейшее развитие — по решению владельца.
