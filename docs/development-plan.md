# План развития

Разработано 2026-09-05 на перенесённом коде main (после v1.0.2 предшественника).
Формат записей: жалоба пользователя от первого лица · ожидаемое поведение ·
оценка объёма · шаг курса, который возьмёт задачу в работу.

Кандидаты проверялись воспроизведением на локальном запуске основного кода;
неподтверждённые кандидаты в план не вошли (см. «Исключено»).

## Баг 1 — Непонятный отказ при длинном email

**Жалоба.** «Записалась с рабочего адреса — у меня домен с несколькими
поддоменами и длинным префиксом. Вставила адрес в форму, как обычно, а потом
оказалось, что он обрезался: подтверждение пришло на какой-то огрызок, до
коллеги письмо не дошло. Нигде не сказано, какой длины адрес вообще помещается:
ни при вводе, ни в правилах записи — а у имени и заметок предел честно написан.
Мы так и не поняли, где граница и что делать.»

**Воспроизведено** (2026-09-05, локальный запуск main): POST брони с email
длиной 255 символов → `400` «Поле «email»: слишком длинный» (без указания
предела); 254 символа → `201`. Лимит 254 есть в серверной валидации и в поле
формы, но нигде не объявлен публично: описание API для email лимита не содержит
(для имени и заметок — содержит, и обе стороны его соблюдают), форма обрезает
ввод молча, текст ошибки предел не называет.

**Ожидаемое поведение.** Лимит email объявлен в описании API так же, как лимиты
имени и заметок; подсказка о предельной длине видна у поля до отправки; текст
отказа называет предел.

**Оценка объёма:** S (правка описания API + лимит поля формы + текст ошибки,
со стороны сервера поведение не меняется).

**Шаг курса:** issue-жалоба шага 3 (триаж + `/oc explain`), исправление —
PR шага 4 (`/oc fix`, замечания ревью, релиз 1.0.3 после `fix:`).

## Фича 1 — Отмена своей брони

**Жалоба.** «Записалась не на то время — перепутала 15-минутку с получасовой
встречей. На сайте отменить нельзя: после подтверждения страница показывает
только «вы записаны», и всё. Свои записи нигде не собираются — если записалась
на три встречи, помнишь только про последнюю. Приходится писать в чат владельцу
календаря с просьбой „удалите, пожалуйста“, и ждать, пока он увидит и освободит
слот. Вечером перед встречей это особенно обидно.»

**Основание** (проверено в текущем коде): API умеет только создавать бронь и
списком смотреть (список — для владельца); операции отмены нет ни в описании
API, ни на сервере; гостю после записи негде собрать и посмотреть свои брони.

**Ожидаемое поведение.** Гость видит свои брони (например, по ссылке/коду,
полученному при записи) и может отметить нужную «больше не приходит»; слот
сразу становится свободным и видимым другим; отменяет по-прежнему только сам
владелец записи.

**Оценка объёма:** M (новая операция API + серверное удаление с освобождением
слота + место в интерфейсе + сквозная проверка).

**Шаг курса:** issue-жалоба шага 3 (автотриаж), реализация — PR шага 4.

## Исключено из плана

- **Гонка двух вкладок («свободно» стало «занято»)** — воспроизвести как баг
  не удалось: сервер атомарно отвечает `409` (проверено параллельными POST),
  фронт перехватывает `slot_conflict`, показывает баннер и перезапрашивает
  сетку; «протухание» слота через полночь (`slot_out_of_window`) обработано
  так же. В плане не нуждается.
- **Напоминание о встрече / список прошедших** — не воспроизведено/не
  подтверждено пользователем как потребность; обязательный минимум (1 баг +
  1 фича) закрыт выше. Отложено без срока.
