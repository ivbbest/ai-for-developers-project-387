# Спека: API-контракт (Design First)

Статус: готово — этап 1 реализован: TypeSpec в `contract/`, артефакт
`contract/dist/openapi.yaml` (коммитится), smoke по Prism зелёный
(`./scripts/dev.sh npm run smoke -w @cal-com/contract`); реализация бэкенда
(этап 3) сверена с этим контрактом через prism-proxy (`npm run contract:check -w backend`).
Связанный issue: https://github.com/ivbbest/ai-for-developers-project-386/issues/6
(предшественник этого репозитория: контракт разрабатывался там)
Дата: 2026-09-01

## Цель

Зафиксировать поведение системы (владелец + гость) и API-контракт в TypeSpec,
который станет единым источником правды для независимой реализации фронтенда
и бэкенда.

## Глобальные решения контракта

| № | Решение | Обоснование |
|---|---|---|
| C1 | Префикс API — `/api` (`@server` в TypeSpec) | в проде один контейнер: бэк раздаёт статику фронта + API; префикс разводит маршруты и упрощает SPA-fallback и Vite-proxy в dev |
| C2 | Часовой пояс сервиса — фиксированная константа `Europe/Moscow` (MSK) | окна «09:00–18:00» и «сегодня» — локальные понятия; без константы браузер гостя конвертирует UTC и ломает сетку. В API время — `utcDateTime`; фронт форматирует **в MSK**, а не в поясе браузера |
| C3 | Рабочие часы — константа 09:00–18:00 MSK, все 7 дней недели | по лендингу референса; выходные не исключаем (нет требования) |
| C4 | Окно записи — 14 календарных дней, включая сегодня (сегодня … сегодня+13) | точная трактовка «14 дней с текущей даты»; дата считается в MSK |
| C5 | Идентификаторы: у EventType — читаемый `id` задаёт владелец (паттерн `^[a-z0-9-]{1,40}$`), у Booking — server-side uuid | формулировка курса: «владелец задает id»; читаемый id стабилен в seed/e2e; броням внешний id не нужен |
| C6 | `slug` — нет; `DELETE /event-types` — нет; `GET /event-types/{id}` — нет | вне требований курса (YAGNI); каталог отдаёт все поля для карточки |
| C7 | Ошибки — единая модель `Error { code, message }`; коды: `validation`, `not_found`, `slot_conflict`, `slot_out_of_window`, `payload_too_large`, `duplicate_id`, `server_error`; **все** ответы `/api/*` (4xx/5xx) — только она: дефолтные обработчики Express (413 body-parser, 404 неизвестного `/api/*`-пути, 5xx) оборачиваются единым JSON-хендлером | валидируемый контракт для двух независимых реализаций; иначе на 413/неизвестном пути фронт получает HTML вместо `Error` (N2) |

## Доменные сущности

### Owner (владелец календаря)
```
{ name: string, email: string }   // фиксированный профиль, вне API
```
Один заранее заданный профиль (по курсу — без регистрации и авторизации);
используется в админской части. В контракте — документационная сущность:
отдельных ручек и полей нет, админ-эндпоинты (`GET /api/bookings`,
`POST /api/event-types`) молча принадлежат владельцу. В TypeSpec — `@doc`
на сервисе/админ-интерфейсе, **не** отдельная модель: модель, не
используемая ни в одной операции, не попадает в сгенерированный
`openapi.yaml` (эмиттер выводит только referenced-схемы) — N4.

### EventType
```
{ id: string (паттерн C5), title: string (1–80), description?: string (≤ 500),
  durationMinutes: int32 }   // 5–540, кратно 5
```
Создаёт владелец (`POST /event-types`). Seed: `meet-15` («Встреча 15 минут»),
`meet-30` («Встреча 30 минут») — идемпотентно при старте бэка.

### Slot
```
{ start: utcDateTime, end: utcDateTime, status: "available" | "booked" }
```
Сетка дня: от 09:00 MSK с шагом `durationMinutes`, пока `end ≤ 18:00 MSK`.
Прошедшие слоты текущего дня (start < now) из ответа **исключаются**.
Занятые слоты **возвращаются со статусом `booked`** — иначе UI «Статус слотов»
(Свободно/Занято, см. project-understanding §3) нереализуем.

### Booking
```
{ id: uuid, eventTypeId: string, start: utcDateTime, end: utcDateTime,
  name: string (1–120), email: string (валидный, ≤ 254), notes?: string (≤ 2000),
  createdAt: utcDateTime }
```
Поля гостя плоские (name/email), а не вложенный `attendee` — проще клиент и валидация.

## Эндпоинты

### Публичные (гость)

| Метод | Путь | Назначение | Успех | Ошибки |
|---|---|---|---|---|
| GET | `/api/event-types` | Каталог типов (id, title, description, durationMinutes) | 200 `EventType[]` | — |
| GET | `/api/event-types/{id}/slots?date=YYYY-MM-DD` | Сетка слотов дня со статусами (`date` — обязательный `@query`) | 200 `Slot[]` | 404 тип не найден; 400 дата кривая или параметр не передан (E20); `slot_out_of_window` — дата вне C4 (200 c `[]` **не** отдаём, чтобы фронт различал «нет слотов» и «вне окна») |
| POST | `/api/bookings` | Создать бронь | 201 `Booking` | 400 валидация; 404 типа нет; `slot_conflict` → 409; 413 `payload_too_large` (E18) |

Тело `POST /api/bookings` (`BookingCreate`):
```
{ eventTypeId: string, start: utcDateTime, name, email, notes? }
```
`end` сервер вычисляет сам: `start + durationMinutes(eventType)`; клиент его не шлёт.

### Админка (владелец)

| Метод | Путь | Назначение | Успех | Ошибки |
|---|---|---|---|---|
| GET | `/api/bookings` | Предстоящие встречи всех типов (`start ≥ now`), сортировка по `start` | 200 `Booking[]` | — |
| POST | `/api/event-types` | Создать тип | 201 `EventType` | 400 валидация; 409 `duplicate_id` (id занят); 413 `payload_too_large` (E18) |

## Правила занятости (ядро)

1. Конфликт — **пересечение интервалов**, не равенство времени:
   `newStart < existingEnd && newEnd > existingStart` по всем броням (тип не учитывается).
   Контрпример к наивному `UNIQUE(start)`: бронь 30-мин типа 09:00–09:30 и запрос
   15-мин типа на 09:15 — starts разные, интервалы пересекаются → обязано быть 409.
2. Индекс `UNIQUE(start)` **недостаточен**; проверка — SELECT пересечений + INSERT
   в одной транзакции (`better-sqlite3` — синхронная транзакция в одном процессе
   закрывает и гонку параллельных POST).
3. `start` в запросе обязан совпадать со слотом сетки этого типа (выровнен по 09:00 MSK,
   кратно duration, в окне C4, не в прошлом) → иначе 400 `slot_out_of_window`/`validation`.
4. Ответ `slots` считается так же: сетка типа минус пересечения с бронями (статус `booked`).

## Крайние случаи (зафиксированы до кода; каждый = тест)

| # | Ситуация | Ожидаемое поведение |
|---|---|---|
| E1 | Стык интервалов 09:00–09:15 и 09:15–09:30 | **не** конфликт (строгие `<`/`>` в формуле) |
| E2 | Двойной клик/две вкладки: два POST с одним start | ровно один 201, второй 409; фронт не считает 409 успехом, показывает занятость и обновляет сетку |
| E3 | Страница висела до полуночи, `start` стал прошлым | 400 `slot_out_of_window`; «сегодня» считается сервером на момент запроса (MSK); `message` — «время слота уже прошло», отличный от E5 («дата вне окна записи»): фронт по нему делает рефреш сетки, а не подсказку о дате |
| E4 | `date` не парсится / 29.02 невалидный | 400 `validation` |
| E5 | `date` = сегодня+13 / +14 / вчера | OK / 400 `slot_out_of_window` / 400 `slot_out_of_window` (окно включительно с обеих сторон: сегодня … сегодня+13) |
| E6 | Неизвестный `eventTypeId` в slots/booking | 404 (проверка типа раньше валидации даты/start) |
| E7 | `start` вне сетки (09:07) или не кратно duration | 400 `validation` |
| E8 | Неизвестные поля в теле POST | 400 `validation` (строгая схема, zod `.strict()`) — ловит опечатки клиентов |
| E9 | Не-JSON тело / Content-Type другой | 400 `validation`; тело > 64 КБ → 413 `payload_too_large` (express limit; ответ — `Error`, см. E18) |
| E10 | name/notes: trim, пустые после trim → 400; unicode/кириллица/эмодзи — проходят; максимумы по спеке (email — 254, спека обновлена в PR #34) | сервер нормализует trim |
| E11 | email: trim; валидация простая (regex), регистр сохраняется как введён; максимум 254 по контракту, считается по сырой строке до trim (как name/notes в E10) | 400 при невалидном/переборе |
| E12 | `durationMinutes` 540 → 1 слот/день; 545 или 0 или 13 → 400 | кратно 5, 5–540 |
| E13 | POST /event-types с id seed-типа (`meet-15`) | 409 (уникальность) |
| E14 | Повторный старт сервера на существующей БД | seed идемпотентен, дублей нет, брони целы |
| E15 | Параллельные POST на пересекающиеся интервалы разных типов | один 201, остальные 409 (транзакция) |
| E16 | `GET /api/bookings` | только `start ≥ now` (MSK), сортировка по `start`; пагинация не нужна (объём окна мал) — зафиксировать как ограничение дизайна |
| E17 | Trailing slash `/api/event-types/` | не нормативно; фронт шлёт точные пути из контракта |
| E18 | Тело > 64 КБ на любом POST (413) | `Error { code: "payload_too_large" }` в JSON — дефолтный HTML-ответ Express (body-parser limit) оборачивается единым 4xx-хендлером |
| E19 | Неизвестный путь `/api/*` (напр. `/api/whatever`) | 404 `Error { code: "not_found" }` в JSON; SPA-fallback настроен только на не-`/api` GET, поэтому `/api/*` не должен «проваливаться» в `index.html` или дефолтный Express-404 |
| E20 | `GET /slots` без параметра `?date=` | 400 `validation` (`date` обязателен: в TypeSpec — `@query` без `?`) |

## Модель ошибок (общая)

```
Error { code: "validation" | "not_found" | "slot_conflict" | "slot_out_of_window"
                   | "payload_too_large" | "duplicate_id" | "server_error",
        message: string }   // человекочитаемый, RU
```
Соответствие HTTP: validation→400, not_found→404, slot_conflict→409,
slot_out_of_window→400, payload_too_large→413, duplicate_id→409,
server_error→500. `duplicate_id` добавлен при реализации контракта (этап 1):
для 409 «id занят» в C7 не было кода, а `slot_conflict` — про слоты, не про id.
`server_error` — при реализации бэкенда (этап 3): требование «все ответы /api/*
(4xx и 5xx) — только эта модель» было невыполнимо для необработанных 5xx —
в закрытом enum не было кода для внутренней ошибки. Все ответы `/api/*`
(4xx и 5xx) — только эта модель: единый JSON-хендлер бэкенда оборачивает
дефолтные ответы Express (413 от body-parser, 404 unmatched-маршрута,
необработанные 5xx) — кейсы E18–E19.

## Правила реализации (следуют из контракта)

- Dev-режим фронта: Vite-proxy `/api` → бэкенд (CORS не нужен). Требование курса
  «корректно работать с отдельно запущенным бэкендом» проверяется на этапе 3
  (work-plan 3.5, dev-связка бэк+фронт): на этапе 2 бэкенда ещё нет, фронт
  работает против стаба контракта (work-plan 2.1b) — требование к нему
  неприменимо (N6).
- Единый JSON-хендлер ошибок: все ответы `/api/*` (4xx/5xx) — модель `Error`
  (C7, E18–E19); SPA-fallback — только не-`/api` GET.
- Прод: тот же Express раздаёт `frontend/dist` + SPA-fallback на одну порту `PORT`
  (см. project-understanding §11 решение 9).
- Хранение: SQLite (`better-sqlite3`), канонический файл `backend/data/app.db`
  (gitignore — вся папка `backend/data/`, т.к. WAL добавляет `*.db-wal`/`*.db-shm`);
  эфемерность диска
  Render принята осознанно — seed при старте (project-understanding §11 решение 10).
- Порт не хардкодится: `PORT` из env; при `EADDRINUSE` — человекочитаемая ошибка
  «порт X занят, укажи свободный (PORT=…)» и ненулевой exit-code (в dev это частая
  коллизия: 3001/5173/4010 уже заняты другими процессами).
- Админ-ручки без авторизации (требование курса): `GET /api/bookings` публично отдаёт
  name/email — риск принят, в демо только seed-значения (project-understanding §8).
