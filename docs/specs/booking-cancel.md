# Спека: отмена своей брони

Статус: готово
Связанный issue: #12
Дата: 2026-09-06

## Цель

Гость, записавшийся не на то время, отменяет бронь сам — без чата с владельцем.
Операция `DELETE /api/bookings/{id}`: слот сразу освобождается, гость получает
номер брони при записи и отменяет по ссылке с ним.

## Критерии приёмки

- [x] В контракте есть `DELETE /api/bookings/{id}`; идентификатор гость получает
      при записи: номер и ссылка на страницу отмены — на странице подтверждения.
- [x] После отмены слот «Свободно» в сетке и берётся другой записью (backend-тест,
      смоук стаба, e2e-сценарий «записался → отменил → слот свободен»).
- [x] Чужую бронь отменить нельзя: операции чтения одной брони нет, неизвестный
      id — 404; повторная отмена — идемпотентные 204, не 500.
- [x] UI: на странице после записи виден способ отменить; e2e зелёный (12 сценариев).
- [x] Тесты слоёв обновлены: contract-smoke 27→30, смоук стаба 46→54,
      vitest бэка +4, contract:check 9→13, e2e +3; CI-гейт зелёный.

## Ограничения

- Авторизации нет (по курсу): id брони — единственная «подпись» гостя
  (capability-модель). Утечка номера = отмена брони; для учебного сервиса
  принято осознанно.
- Отменяет только гость по своему номеру: кнопки отмены в админке нет —
  по формулировке плана («отменяет по-прежнему только сам владелец записи»).
- Состояние «уже отменена» не различается с «не существует» (оба неразличимы
  для неизвестного id; для отменённой — 204): эндпоинт не должен подтверждать
  существование чужих броней.

## Заметки / решения

- Мягкое удаление (`status='cancelled'`, CHECK в схеме): повторная отмена
  идемпотентна, строка остаётся историей; все читалки (`findOverlaps`,
  `listUpcoming`) фильтруют `active`. Миграция существующих БД — ALTER по
  `PRAGMA table_info` в `migrate()`: `CREATE TABLE IF NOT EXISTS` новые
  колонки не добавляет, а локальные файлы/volume переживают рестарт.
- `Response<204>` в TypeSpec оформлять только через `NoContentResponse` из
  `@typespec/http`: именованная модель-наследник заводит в openapi `content`
  с пустой схемой, и prism-proxy считает пустое тело бэкенда нарушением.
- Стаб контракта — зеркало семантики: физическое удаление + `cancelledIds`
  (in-memory аналог tombstone), коды совпадают с бэкендом один в один.
- 204 во фронтенд-клиенте: `res.json()` на пустом теле бросает SyntaxError —
  `request()` возвращает `undefined` до парсинга.

## Рассмотрено (опционально)

- «Мои записи» гостя (список по email) — не делаем: email не подтверждается,
  список по нему стал бы чужим броням окном отмены. Номер брони в письме/UI —
  минимально достаточный UX для жалобы.
