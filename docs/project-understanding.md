## 1. Что за проект

Учебный проект курса «ai-for-developers»: сервис бронирования звонков по мотивам
Cal.com. Вся разработка ведётся ИИ-агентами; человек проверяет и направляет.
Подход — **Design First**: сначала контракт API, затем независимо фронтенд и бэкенд.

Ограничение итогового результата: приложение должно собираться в Docker-образ и
запускаться в контейнере по порту из переменной `PORT`.

## 2. Предметная область (по Cal.com → упрощённо для нашего сервиса)

Сценарий: владелец публикует доступное время → гость выбирает слот → запись.

| Понятие | Описание в нашем сервисе |
|---|---|
| Event Type | Шаблон встречи: `id`, название, описание, длительность в минутах |
| Slot | Конкретный доступный интервал (длина = длительность типа события) |
| Booking | Запись гостя на слот: имя, email, время, заметки |

Роли (без авторизации):
- **Владелец календаря** — один заранее заданный профиль, используется в админской части.
- **Гость** — бронирует без аккаунта и без входа.

Действия:
- Владелец: создаёт типы событий; смотрит страницу предстоящих встреч (все типы в одном списке).
- Гость: смотрит каталог типов событий (название, описание, длительность); выбирает тип,
  открывает календарь, выбирает свободный слот в ближайшие 14 дней; создаёт бронирование.

Правила:
- Занятость: на одно время нельзя создать две записи (даже разных типов).
- Окно записи: слоты на 14 дней с текущей даты; гость записывается только на свободный слот.
- Нет авторизации, ЛК, внешних календарей (намеренно).

## 4. Архитектура (Design First / API-контракт)

Frontend и Backend реализуются раздельно, связь — через **API-контракт**.

- Контракт пишется в **TypeSpec** (https://typespec.io/) → генерация OpenAPI 3.
- Фронтенд разработки без бэкенда — через **стаб контракта** (in-memory мок
  с состоянием: «бронь → слот „Занято“», seed, 409); **Prism** — smoke по схеме
  (коды 404/409 через `Prefer: code=NNN`) и валидационный прокси: состояния
  он не хранит (аудит N1).
- Подход реализаций: типизированный TS предпочтителен для агентной работы.

Эндпоинты (итог ревью, детали — `docs/specs/api-contract.md`):
- Префикс `/api` (в проде один контейнер: бэк + статика фронта).
- `GET /api/event-types` — публичный каталог; `POST /api/event-types` — владелец (409 id занят).
- `GET /api/event-types/{id}/slots?date=YYYY-MM-DD` — сетка слотов дня **со статусами**
  `available|booked` (не «только свободные» — иначе UI «Свободно/Занято» нереализуем).
- `POST /api/bookings` — создать бронь (`eventTypeId + start`, `end` считает сервер);
  201 / 400 / 404 / 409 (`slot_conflict`).
- `GET /api/bookings` — предстоящие (`start ≥ now`), все типы, по времени.
- Занятость = **пересечение интервалов** (`newStart < exEnd && newEnd > exStart`),
  не равенство времени; `UNIQUE(start)` недостаточен (типы 15/30 мин).
- Часовой пояс сервиса — фиксированный `Europe/Moscow`; время в API — UTC,
  фронт форматирует в MSK, а не в поясе браузера.

## 5. Стек и инструменты (решение)

### Контракт (Design First)
- **TypeSpec** → генерация **OpenAPI 3** (`@typespec/openapi3`). OpenAPI — единый источник правды.

### Фронтенд
- **Vite + React + TypeScript** — быстрый dev, типизация, стандарт индустрии.
- **shadcn/ui** (Radix + Tailwind) — готовые `calendar`, `date-picker`, `form`, `dialog`,
  `table`, `sidebar`; код компонентов в репозитории (читаем агентом); есть MCP-сервер.
  *(Mantine — отклонён: выбран shadcn из-за календаря и «агентности»; финально)*.
- **react-router** — роутинг страниц.
- **TanStack Query — не берём** (финально): запросов мало, кэш не нужен — тонкий
  fetch-клиент по контракту проще и читаемее.
- Во время разработки без бэкенда — **стаб контракта** (этап 2, 2.1b: in-memory
  с состоянием); **Prism** — smoke по схеме (`Prefer: code=`) и прокси-валидация.

### Бэкенд
- **Node + Express** + **TypeScript** — типизированный, тот же язык, что фронт;
  Express проще для учебного проекта *(Fastify — отклонён, финально)*.
- **zod** — валидация входящих данных по контракту.

### Хранение
- **SQLite** через `better-sqlite3` — простое файловое хранилище (без внешнего сервиса),
  данные сохраняются между рестартами, легко упаковать в Docker.

### e2e + релизы
- **Playwright** — браузерные сценарии бронирования.
- **Conventional Commits** + **release-please-action** v5 (Release-PR, CHANGELOG, SemVer).
- CI — **GitHub Actions** (e2e на `node:24` + `playwright install`, не на mcr-образе — см. `e2e.yml`; hexlet-check не трогаем).
- **MCP** (опционально): Playwright MCP, Chrome DevTools MCP.

### Деплой
- **Docker** (multi-stage, читает `process.env.PORT`), публикация — **Render** (free tier)
  или **Railway** как запасной; публичная ссылка.

### Окружение разработки (решение ревью 2026-09-01)
- Все dev-команды (`tsp compile`, `vite build`, установка `better-sqlite3`, тесты) —
  **в контейнере `node:24`** (volume на проект): в WSL `node` на PATH не виден
  (npm — Windows-обёртка), DrvFs `/mnt/e` медленный и с проблемами блокировок SQLite,
  а Linux-контейнер совпадает с прод-образом (нативные модули консистентны).
  Обёртка/скрипт — см. §11 решение 7.

> Статус: стек **финализирован 2026-09-01** (решения §11 1–16, ревью + аудит
> 2026-09-01): Express — финально (не Fastify), shadcn/ui —
> финально (не Mantine), TanStack Query — не берём, мок этапа 2 — стаб контракта
> (Prism — smoke/прокси). Формальное подтверждение — в Issue этапа 1 (шаг 1.1).

## 7.1. Официальные требования по шагам (из файлов-инструкций)

Источники: `design-first.txt`, `frontend.txt`, `backend.txt`, `docker.txt`.

### Дизайн / контракт (`design-first.txt`)
- Подход **Design First**: контракт фиксирует границу между фронтом и бэком,
  единый источник правды.
- Инструмент — **TypeSpec** (компактный язык) → генерация **OpenAPI** через
  emitter `@typespec/openapi3`.
- Описать доменные сущности: владелец, тип события, слот, бронирование, публичный сценарий гостя.
- Проверить, что спека покрывает сценарии владельца и гостя.
- **Результат**: в репозитории есть TypeSpec-спецификация, фиксирующая контракт.

### Фронтенд (`frontend.txt`)
- Фронтенд — отдельная часть приложения, данные/действия **только через API по контракту**.
- Интерфейс должен корректно работать с отдельно запущенным бэкендом.
- Рекомендации курса (не обязательны): TypeScript + Vite, UI — shadcn/ui или Mantine,

- **Результат**: появился UI приложения.

### Бэкенд + e2e + релизы (`backend.txt`)
- Интеграционные/сценарийные проверки на уровне пользовательских сценариев,
  рекомендуется **Playwright** (реальный браузер), язык по выбору (типизированный лучше для агентов).
- Охватить основной сценарий бронирования от начала до конца.
- CI: запуск тестов в GitHub Actions.
- Формат коммитов — **Conventional Commits** (`feat:`, `fix:` и т. д.).
- **release-please** как GitHub Actions workflow (release-please-action): release-PR
  с changelog и версией по правилам SemVer.
- После мёржа в основную ветку release-please создаёт/обновляет release-PR.
- **Результат**: автоматические e2e-проверки + авторелизы/changelog.

### Docker + деплой (`docker.txt`)
- В репозитории — **Dockerfile**; по нему собирается образ и запускается приложение.
- При запуске контейнера приложение стартует автоматически.
- Запуск по порту из переменной окружения **`PORT`** (используется при деплое и в авто-проверке).
- После деплоя — **публичная ссылка**.
- Платформа: **Render** (рекомендуется, free tier) или **Railway** как запасной
  вариант; важен работающий сервис по PORT, а не конкретная платформа.
- **Результат**: есть Dockerfile, приложение запускается в контейнере по PORT.

## 8. Открытые вопросы / заметки

Развязано ревью 2026-09-01 (детали — §11, `docs/specs/api-contract.md`):

- Стек **финализирован 2026-09-01** (§5, §11 1/15/16): TypeSpec→OpenAPI;

  Docker → Render (запасной Railway); мок этапа 2 — стаб контракта. Альтернативы
  (Fastify, Mantine, TanStack Query) отклонены.
- Окно «14 дней с текущей даты» → сегодня … сегодня+13, дата в MSK (решение C4 спеки).
- «Фиксированные 30-мин слоты 09:00–18:00» на лендинге — маркетинговое описание;
  фактические слоты = сетка по длительности типа в рабочих часах 09:00–18:00 MSK.
- Отдельный профиль владельца — константа/конфиг без авторизации (по курсу).

Принятые риски (осознанно, не чиним):

- **Админ-ручки публичны**: `GET /api/bookings` без авторизации отдаёт name/email
  наружу по публичному URL; `POST /api/event-types` доступен любому. Курс запрещает
  авторизацию — в демо используем только seed/фиктивные данные, не реальные контакты.
- **Эфемерный диск Render free tier**: SQLite-файл стирается при рестарте/деплое.
  Принимаем: seed при старте пересоздаёт типы; брони живут до рестарта. Миграция на
  Postgres — отдельная задача, контракт от хранилища не зависит.
- **Утверждение §6** «у Render/Railway официальных MCP нет» — перепроверено 2026-09-02
  (шаг 0.2 плана): неверно, исправлено в §6. У обеих платформ официальный MCP есть
  (Render — сервер `render-oss/render-mcp-server`, Railway — встроен в CLI
  `railway mcp`). На шаг 5 не влияет: деплой остаётся через CLI/UI, MCP опционален.

### Шаг 1 — Контракт (TypeSpec → OpenAPI)

**Подзадачи и реализация:**
1. **GitHub Issue** «API-контракт»: перенести текст из `docs/specs/api-contract.md`
   (решения C1–C7 уже в нём).
2. ~~Уточнение домена (`grill-me`)~~ — вопросы закрыты ревью 2026-09-01:
   слот = интервал с `status` (не «только свободные»), конфликт = пересечение

   Все ответы — в `docs/specs/api-contract.md`.
3. **Инициализация TypeSpec** (все команды — в контейнере `node:24`, §5):
   - каркас вручную или `tsp init` (шаблон REST API): `main.tsp`, `package.json`.
   - корневой `package.json` монорепо: NPM workspaces `contract`, `frontend`,
     `backend` (`e2e/` — отдельно, решения 3–4; шаг 1.3 плана, аудит F2).
   - Пакеты: `@typespec/compiler`, `@typespec/http`, `@typespec/openapi3`, `@typespec/rest`
     — **версии пинить**; эмиттер openapi3 по умолчанию пишет JSON — в `tspconfig.yaml`
     задать `file-type: yaml` + `output-file: openapi.yaml` (иначе `dist/openapi.yaml` не появится).
4. **Описание сущностей** (`model`):
   - `EventType { id, title, description?, durationMinutes }` (id читаемый, паттерн)
   - `Slot { start: utcDateTime, end: utcDateTime, status: "available" | "booked" }`
   - `Booking { id, eventTypeId, start, end, name, email, notes?, createdAt }`
   - `BookingCreate { eventTypeId, start, name, email, notes? }` (без `end` — считает сервер)
   - `Error { code, message }` — единая модель всех 4xx/5xx `/api/*` (коды см. спеку,
     включая `payload_too_large` → 413)
   - `Owner` — документационная сущность (спека, «Доменные сущности»): фиксированный
     профиль вне API; в TypeSpec — `@doc` на админ-интерфейсе, **не** отдельная модель:
     не используемая в операциях модель не попадает в `openapi.yaml` (аудит N4)
5. **Эндпоинты** (`interface` + `@route/@get/@post/@path/@query/@body`, `@server("/api")`):
   - `GET /api/event-types` — каталог; `POST /api/event-types` — 201/400/409.
   - `GET /api/event-types/{id}/slots?date=YYYY-MM-DD` — 200 `Slot[]`/400/404
     (`date` — обязательный `@query`: без него 400 `validation`, спека E20).
   - `POST /api/bookings` — 201 `Booking`/400/404/409.
   - `GET /api/bookings` — 200 `Booking[]` (предстоящие, по `start`).
6. **Генерация**: `npx tsp compile . --warn-as-error` → `contract/dist/openapi.yaml`
   (emitter `@typespec/openapi3`).
7. **Проверка**: без ошибок компиляции; `openapi.yaml` валиден; smoke через
   `npx @stoplight/prism-cli contract/dist/openapi.yaml` + `curl` по всем ручкам
   (200/201/400/404/409; 404/409 — через `Prefer: code=NNN`: Prism без состояния,
   отдаёт заготовленный ответ по схеме); покрыты сценарии владельца и гостя.
8. **Обновить** `docs/specs/api-contract.md` (статус → «готово», финальный список ручек).

### Шаг 2 — Фронтенд

**Стек** (финально, §5): Vite + React + TypeScript; UI — shadcn/ui; запросы —
тонкий fetch-клиент по контракту (без TanStack Query).

**Подзадачи:**
1. **Каркас**: `npm create vite@latest` (React+TS) в папке фронта (напр. `frontend/`);
   команды — в контейнере `node:24` (§5); dev-связь с бэком — **Vite-proxy `/api`**
   (CORS не нужен), базовый URL клиента — относительный.
2. **UI-компоненты** через shadcn MCP (`npx shadcn@latest mcp`): `button, card, calendar,
   date-picker, dialog, form, input, table, sidebar, select, badge`.
3. **Типизированный клиент API** по OpenAPI (генерация клиента или ручной тонкий слой fetch
   по контракту). На время разработки — **стаб контракта** (`contract/mock-server`,
   in-memory с состоянием — work-plan 2.1b); Prism — только smoke по схеме, stateful
   «бронь → Занято» на нём невозможен (аудит N1).
   Время на UI форматировать **в фиксированной TZ сервиса (MSK)**, не в поясе браузера
   (`Intl` с `timeZone: 'Europe/Moscow'`); слоты рисовать по `status` (Свободно/Занято).
4. **Страницы/роуты** (react-router):
   - `/` — лендинг «БЫСТРАЯ ЗАПИСЬ НА ЗВОНОК» (блок возможностей, CTA «Записаться»).
   - `/book` — каталог типов событий (карточки: название, описание, длительность).
   - `/book/:typeId` — выбор даты (календарь, 14 дней) + «Статус слотов» (Свободно/Занято).
   - `/book/:typeId/confirm` — форма: Имя, Email, заметки → «Подтвердить запись»
     (409 → показать ошибку и обновить сетку слотов).
   - `/book/:typeId/success` — «Бронь подтверждена. До встречи!».
   - `/admin` — «Предстоящие события» (список броней всех типов).
   - `/admin/new-type` — **форма создания типа события** (id, название, описание,
     длительность) — требование курса «владелец создаёт типы»; на скриншотах экрана нет,
     делаем минимальную форму в стиле админки.
5. **Реализация UI** по скриншотам из `input/` (лендинг, каталог, календарь+слоты, форма,
   подтверждение, админ; русский язык).
6. **Проверка**: `npm run build` без ошибок; dev-сервер; ручной проход сценария
   бронирования против стаба (с этапа 3 — против реального бэка; включая создание
   типа в `/admin/new-type`).

### Шаг 3 — Бэкенд

**Стек**: Node + Express + TypeScript (типизированный — удобно агентам);
хранение — SQLite (`better-sqlite3`) + идемпотентный seed при старте (§11 решения 1, 10).

**Подзадачи:**
1. **Каркас**: `backend/` с TS, роуты по OpenAPI-контракту (префикс `/api`);
   чтение `process.env.PORT`; TZ сервиса — константа `Europe/Moscow` (не серверная).
2. **Сущности/хранение**: репозитории `EventType`, `Booking`; **идемпотентный seed**
   типов событий при старте (`meet-15`, `meet-30` — как в примере); SQLite-файл
   может быть пуст/стёрт (Render) — seed пересоздаёт типы.
3. **Логика сетки слотов**:
   - окно: сегодня … сегодня+13 (календарные дни в MSK);
   - сетка: 09:00 MSK, шаг = durationMinutes типа, пока `end ≤ 18:00 MSK`;
   - прошедшие слоты текущего дня исключаются; каждый слот со `status`
     (пересечения с бронями → `booked`); ответ — вся сетка дня, не только свободные.
4. **Создание брони**: zod-валидация (имя, email, start из сетки типа и в окне);
   `end = start + duration`; **проверка пересечений**
   (`start < exEnd && end > exStart`, все типы) + вставка **в одной транзакции**
   (`better-sqlite3` — синхронная; `UNIQUE(start)` от гонки не спасает);
   конфликт → 409 `slot_conflict`.
5. **Типы событий**: POST — валидация паттерна id и уникальности (409), длительности 5–540.
6. **Админ-список**: предстоящие (`start ≥ now`), все типы, сортировка по `start`.
7. **Раздача фронта (прод-режим)**: `express.static(frontend/dist)` + SPA-fallback
   (не-`/api` GET → `index.html`) — единое приложение на `PORT`; это же — «приложение»
   для Docker-проверки курса. В dev — только API + Vite-proxy.
8. **Проверка**: юнит-тесты на правила (окно, сетка, пересечение/409, трансакция);
   запуск сервера и сверка ответов с контрактом (`prism proxy` для diffs);
   smoke: создание брони поверх занятого интервала другим типом → 409.

**Подзадачи:**

### Шаг 5 — Docker + деплой

**Подзадачи:**
1. **Dockerfile** (multi-stage, Node):
   - stage build: сборка фронта (`vite build`) и бэка (`tsc`);
   - stage prod: копирование артефактов, `ENV PORT=3000`, `EXPOSE 3000`
     (фиксированный: `PORT` читается приложением из env, а `EXPOSE` — только
     документация образа),
     `CMD` запускает **единое приложение** — бэк, раздающий API + `frontend/dist`
     по `process.env.PORT` (не два процесса); сборка/проверка — в Linux-окружении (§5).
2. **Локальная проверка**: `docker build -t cal-com .`; `docker run -p $PORT:$PORT -e PORT=...`;
   `curl` к порту — сервис отвечает.
3. **Деплой на Render** (основной): New Web Service → Build from Dockerfile → Port из PORT →
   env PORT → Deploy → публичный URL `https://<service>.onrender.com`.
   Запасной — Railway (тот же образ, PORT, `*.up.railway.app`). Официальные MCP есть
   (§6), но деплой — через CLI/UI: MCP для курса не требуется.
4. **Публичная ссылка** — в README.
5. **Проверка**: сервис отвечает по публичному URL и порту; приложение автостартует в контейнере.

---

**Итог**: каждый шаг завершается фактической проверкой (build/тесты/контейнер/URL),
обновлением спеки и памяти; коммит-чекпоинты — в рабочую ветку, слияние в `main` —
только пользователь.

### Принципы структуры
- **Монорепо**: `contract/` + `frontend/` + `backend/` (+ `e2e/`) в одном репозитории — единый
  контракт, один Docker-образ, проще для учебного проекта.
- **Design First**: `contract/` — источник правды; `frontend/` и `backend/` опираются на OpenAPI,
  не анализируя код друг друга.
- **Типизация**: общий язык TS; типы фронта по контракту; бэк валидирует через zod.
- **Docker/деплой**: `Dockerfile` собирает всё (build фронта+бэка), запуск по `PORT`.
- **Git-гигиена**: `docs/` — в git; `contract/dist/openapi.yaml` коммитим; `backend/data/*.db`,
  `node_modules` — в gitignore; `input/` — исключён локально (`.git/info/exclude`, не коммитить);
  рабочая память проекта (журнал, уроки, реестр) — в git (курируемая, §11 решение 8); локальные настройки инструментов — вне git.

## 11. Зафиксированные решения (по итогам обсуждения)

| № | Решение | Обоснование |
|---|---|---|
| 1 | Стек (финально, 2026-09-01): фронт Vite+React+TS+shadcn/ui, бэк Node+Express+TS+zod, хранение SQLite (better-sqlite3), контракт TypeSpec→OpenAPI | типизированный, общий язык, простота, удобно для агентов и Docker; Mantine/Fastify/TanStack Query отклонены (§5) |
| 2 | `contract/dist/openapi.yaml` — **коммитить** + CI-проверка синхронизации (`tsp compile` → diff) | Prism, фронт, бэк и e2e используют готовый файл; избегаем рассинхрона |
| 3 | Корневой `package.json` с **NPM workspaces** (`contract`, `frontend`, `backend`) | один `npm install`; общие dev-зависимости; удобно для Docker/агента |
| 4 | **`e2e/` — отдельная корневая папка** (не внутри frontend) | сценарий проходит сквозь фронт И бэк (webServer поднимает оба) |
| 5 | SQLite-файл — `backend/data/*.db` в **gitignore** | локальные данные не в git |
| 6 | Окружение WSL2: node/npm из Windows (`/mnt/c/...`), `node` на PATH не виден | снять решением 7 |
| 7 | **Dev-команды — в контейнере `node:24`** (volume на проект; скрипт-обёртка/compose) | `node` в WSL отсутствует; DrvFs `/mnt/e` медленный + проблемы блокировок SQLite; Linux-контейнер = прод-образ (нативные модули) |
| 8 | **Память проекта — публичная, курируемая** (в git): без секретов и PII; правила и память синхронизированы | решение пользователя; память сессии открыта, но вычитывается |
| 9 | **Прод = один контейнер**: бэк раздаёт `frontend/dist` + SPA-fallback; API под `/api` | требование Docker/PORT (один процесс); префикс разводит маршруты; dev — Vite-proxy, CORS не нужен |
| 10 | **SQLite + идемпотентный seed при старте; эфемерность диска Render принята** | цель курса — цикл по контракту, не персистентность; Postgres — отдельная задача, контракт не зависит |
| 11 | **TZ сервиса — `Europe/Moscow` константой**; API — UTC, фронт форматирует в MSK | иначе браузер гостя конвертирует UTC и ломает сетку 09:00–18:00; референс (админка) показывает наивное время |
| 12 | **`id` типа задаёт владелец** (паттерн `^[a-z0-9-]{1,40}$`, уникальность 409); `slug`/`DELETE`/`GET /{id}` — нет | формулировка курса «владелец задает id»; читаемые id стабильны в seed/e2e; остальное — YAGNI |
| 13 | **Git-workflow**: ветка `<тип>/<тема>` на этап/подэтап, коммит-чекпоинт на каждое существенное изменение, **push/PR/merge — только владелец**; зависимые работы — на паузе; порты не хардкодятся (`PORT`/env, внятная ошибка на `EADDRINUSE`) | решение пользователя 2026-09-01; детали — в git-истории предшественника |
| 14 | **Тесты обязательны слоем на этап** (контракт compile+Prism, vitest-unit бэка, сборка фронта, Playwright e2e); задача = поведение + тест + коммит; временны́е тесты: unit — injectable `now()`, e2e — env `NOW` в webServer или динамический расчёт дат в MSK (аудит N5) | решение пользователя 2026-09-01; матрица слоёв и разбор — в git-истории предшественника |
| 15 | **Мок этапа 2 — in-memory стаб контракта** (`contract/mock-server`, задача 2.1b); Prism остаётся для smoke по схеме (`Prefer: code=` для 404/409) и proxy-валидации бэка (3.4) | Prism не хранит состояние (аудит N1, подтверждён README: Data Persistence не реализована) — сценарий «бронь → „Занято“» на нём нереализуем; стаб — вторичный источник правды, сверяется с контрактом |
| 16 | **Все ответы `/api/*` (4xx/5xx) — модель `Error`** единым JSON-хендлером (код `payload_too_large` → 413; неизвестный `/api/*` → 404 `not_found`; SPA-fallback только не-`/api`); `?date=` обязателен (400 без него); `Owner` — документационная сущность вне API | аудит N2–N4: дефолтные ответы Express и неопределённое поведение ломают договор «две независимые реализации по контракту»; кейсы E18–E20 спеки |
