# Гид владельца: суть проекта, запуск с нуля, на что обращать внимание

Статус: актуален на 2026-09-06 (курс пройден, релиз v1.0.3, фича «отмена
брони» — issue #12, PR #40). Обновлять после изменений агентской обвязки или
настроек репозитория.

Для кого: для владельца репозитория — как пользоваться проектом каждый день,
как поднять всё с нуля на новом репозитории и где здесь грабли.

## 1. В чём суть

Приложение «Календарь звонков» написано в проекте-предшественнике (386) и
сюда перенесено как есть. Сам этот репозиторий проверяет не продукт, а
**процесс**: ИИ-агент работает внутри GitHub как участник команды — отвечает в
issue, разбирает новые задачи, готовит pull request, вносит правки после
ревью и выходит по расписанию с регулярной проверкой деплоя.

Результат каждого шага — **видимый след**: прогон в Actions, ответ агента в
треде, коммиты в PR, артефакт отчёта. «Должно работать» здесь не считается
доказательством; доказательство — ссылка или SHA.

Что сейчас работает:

- четыре воркфлоу агента (интерактив, автотриаж, авторевью, расписание) —
  таблица с событиями, правами и ссылками на прогоны в README;
- релизный цикл: коммиты по Conventional Commits → release-please собирает
  release-PR → после мержа тег и GitHub Release (первый — `cal-com-v1.0.3`);
- ночная проверка деплоя: Lighthouse по публичной ссылке → отчёт-артефакт →
  issue с меткой `perf-report` (дедуп: новые замеры — комментарием в
  существующую задачу);
- автотесты Хекслета (`hexlet-check.yml`) на каждый коммит — файл не трогать.

## 2. Как пользоваться каждый день

| Задача | Действие |
|---|---|
| Разобрать нечёткую задачу | Создать issue жалобой пользователя (без готового решения) — автотриаж разберёт сам. Или позвать в тред: `/oc explain this issue` |
| План/правки по задаче | В трееде: `/oc составь план… с критериями приёмки`; `/oc fix` — агент заведёт ветку `opencode/*` и откроет PR со ссылкой на issue |
| Ревью PR | Авто-ревью приходит на каждый PR владельца; содержательное — комментарием `/oc review` **до мержа** (после squash-мержа с удалением ветки ревью бесполезно) |
| Правки по замечаниям | Комментарий в обсуждении PR (`issue_comment`) или к строке diff (`pull_request_review_comment`) — агент правит ту же ветку |
| Ночная проверка | Ждёт ничего: cron `0 3 * * *`. Ручной прогон — Actions → opencode-schedule → Run workflow; отчёт — артефакты прогона и комментарий/issue `perf-report` |
| Выпустить релиз | Смержить `fix:`/`feat:` в main → дождаться release-PR → смержить его → тег и Release появятся сами |

Мерж-гейт (правило реестра): все проверки зелёные (не pending), замечания
разобраны, `/oc review` в треде. Мержит агент только так; force-операции в
main, удаление remote-веток и правки `hexlet-check.yml` — только владелец.

## 3. Поднять с нуля

### Локально (код и проверки)

Нужен Docker (linux-`node` на хосте не обязателен — всё через обёртку) или
Node.js 24 нативно.

```bash
git clone https://github.com/ivbbest/ai-for-developers-project-387.git
cd ai-for-developers-project-387
npm ci                                        # поднимает workspaces
./scripts/dev.sh npm run compile -w @cal-com/contract
./scripts/dev.sh npm run smoke -w @cal-com/contract
./scripts/dev.sh npm run smoke -w @cal-com/mock-server
./scripts/dev.sh npm test -w backend
./scripts/dev.sh npm run contract:check -w backend
./scripts/dev.sh npm run typecheck -w backend
./scripts/dev.sh npm run build -w backend
./scripts/dev.sh npm run lint -w frontend
./scripts/e2e.sh                              # Playwright, сам поднимет контейнер
docker build -t cal-com .                     # прод-образ
```

Это тот же набор, что крутится в CI (job'ы `e2e.yml`/`contract-sync.yml`) и
что записан в AGENTS.md — агент в Actions читает его оттуда, держать
актуальным.

Запуск дев-связки и прода — README «Запуск»; демо на Render — ссылка там же.

### Настройки репозитория (только руками владельца)

1. **Секреты** (Settings → Secrets and variables → Actions → Secrets):
   `HEXLET_ID` (для автотестов курса) и `OPENCODE_API_KEY` (ключ провайдера
   модели). Значения не должны попадать ни в файлы, ни в логи — в воркфлоу
   только имена переменных.
2. **Переменная** `APP_URL` (вкладка Variables): публичный адрес деплоя для
   ночной проверки. Завершающий слэш допустим — воркфлоу нормализует.
3. **Actions → General**: «Allow GitHub Actions to create and approve pull
   requests» — нужно release-please (PR агентов идут через GitHub App и от
   переключателя не зависят).
4. **GitHub App opencode-agent**: Configure → Add repository (расширять
   доступ существующего приложения, не ставить новое и не использовать мастер
   `opencode github install` — он генерирует свой opencode.yml без фильтра
   автора и с `share: true`).
5. **Лимит расходов** в кабинете провайдера модели — каждый вызов агента
   платный.
6. **Метка** `perf-report` (`gh label create perf-report …`) — для ночных
   задач.

### Деплой (для ночной проверки)

Render (или любой Docker-хостинг): логин `Dockerfile`, `PORT` из env,
бесплатный тариф подходит. Диск эфемерный — после рестарта база чистая с
seed-типами; персистентность — отдельная задача (платный диск или вариант B
из `docs/deploy-global.md`).

### Проверить, что обвязка живая

1. Issue с комментарием `/oc explain this issue` → ответ приложения в треде,
   прогон в Actions (см. строку таблицы README).
2. Новый issue без команды → автотриаж сам оставит разбор.
3. Черновой PR → авто-ревью; `/oc review` → содержательный вердикт.
4. Run workflow у opencode-schedule → артефакты + issue/комментарий
   `perf-report`.
5. Анти-петля: после каждого ответа агента убедиться списком прогонов, что
   нового прогона на тот же тред нет (критерий — 2 минуты тишины).

## 4. На что обращать внимание

- **Заголовок каждого PR — Conventional** (`feat:`/`fix:`/…): squash-мерж
  пишет в main заголовок PR; не-Conventional заголовок тихо ломает релизный
  цикл (release-please не увидит коммитов).
- **Воркфлоу для `pull_request` берётся из head-ветки PR**: замерженный в main
  после открытия PR авторевью на этот PR не сработает.
- **Pending-чек ≠ зелёный**: не мержить при незавершённых проверках, даже
  если содержательное ревью уже APPROVED.
- **Прогоны ботов (`action_required`)**: release-PR от `github-actions`
  требует одобрения прогонов — только через UI, эндпоинта для gh нет.
- **Экшен opencode не подхватывает `GITHUB_TOKEN` сам**: там, где агенту нужен
  `gh` (создать issue/комментарий), токен передаётся явно env шага.
- **Агент не должен коммитить рабочие файлы**: гейт `git status --porcelain`
  после шага агента в schedule-воркфлоу + артефакты через upload-artifact;
  запрет в prompt — не механизм, а намерение.
- **Первый cron после добавления воркфлоу может задержаться или не
  сработать** сутки (best-effort у GitHub) — след ночного запуска проверять
  фильтром `--event schedule`, не подменять dispatch-прогоном.
- **Lighthouse по free-тарифу шумный** (0.93 → 0.88 за полтора часа):
  критерии «стало быстрее» проверять несколькими замерами; холодный старт
  прогревается warm-up-шагом.
- **PII не коммитится**: `backend/data/` (имена/email гостей) в .gitignore;
  демо-данные фиктивные.
- **Язык ответов в публичных тредах — русский** (правило в AGENTS.md, его
  читает и агент в Actions).
- **Скиллы и локальная обвязка** (`.opencode/`, `input/`, `.agents/archive/`,
  `skills-lock.json`) — вне git; единственная архивная папка —
  `.agents/archive/` (локально).
