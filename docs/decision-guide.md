# Гид по проекту: контекст, решения, запуск

> Область действия: перенесённое приложение так, как оно задумывалось и
> строилось в репозитории-предшественнике (386). Решения интеграции агента в
> GitHub-процесс этого репозитория — `docs/agent-decisions.md`.

Документ для тех, кто не присутствовал при разработке: зачем этот проект
такой, какой он есть, как он устроен, как его запустить и почему каждое
решение принято именно так — с альтернативами и честной ценой.

## 1. Контекст: что это за проект

Учебный проект курса Хекслета «AI for Developers». Задание — сервис
бронирования календаря в духе cal.com: владелец заводит типы встреч, гости
выбирают свободные слоты и бронируют время. Специфика курса — способ
работы: код пишется вместе с ИИ-агентом, но правила игры жёсткие —
архитектурные решения фиксируются в документах **до** кода (SDD,
spec-driven development), а не рождаются по ходу. Из этого следует почти
всё необычное в репозитории: контракт важнее реализации, план работ —
исполняемый документ с чекбоксами, каждое существенное изменение — ветка
со своим PR и тестами.

Требования приёмки курса (зафиксаны в анализе входных материалов):

- приложение живёт в Docker, слушает `PORT` из переменных окружения,
  стартует автоматически;
- публичный URL, рабочий сценарий бронирования;
- без авторизации, личного кабинета и внешних календарей — по условию;
- проверка — автотесты hexlet-check и ревью на PR.

## 2. Продукт: что делает интерфейс

Два персонажа, шесть экранов:

| Маршрут | Кто | Что видит |
|---|---|---|
| `/` | гость | лендинг: заголовок, три преимущества, кнопка «Записаться» |
| `/book` | гость | каталог типов событий (карточки: название, длительность, описание) |
| `/book/:typeId` | гость | календарь на 14 дней + сетка слотов дня со статусами «Свободно/Занято» |
| `/book/:typeId/confirm` | гость | форма Имя/Email/заметки, подтверждение |
| `/book/:typeId/success` | гость | «Бронь подтверждена» |
| `/admin`, `/admin/new-type` | владелец | лента предстоящих встреч; создание типа события |

Бизнес-правила, зафиксированные в контракте до кода:

- рабочие часы — 09:00–18:00 по **Europe/Moscow**, все семь дней;
- окно записи — сегодня … сегодня+13 календарных дней MSK;
- шаг сетки равен длительности типа (5–540 минут, кратно 5);
- конфликт — пересечение интервалов (`newStart < existingEnd &&
  newEnd > existingStart`), стык «09:15 к 09:15» конфликтом не считается;
- занятость — по всему календарю: один владелец, одно время, тип события
  на пересечение не влияет;
- время в API — UTC (`utcDateTime`), в интерфейсе — всегда MSK: гость
  из другого пояса видит те же «09:00–18:00», что и владелец.

UI сверен с макетами из `input/` (скриншот-чек по текстам и составу
блоков), язык интерфейса — русский.

## 3. Архитектура

Главная идея — **Design First**: единственный источник правды — контракт.

```
contract/ (TypeSpec)
   │  tsp compile (CI проверяет: артефакт = вывод компилятора)
   ▼
contract/dist/openapi.yaml  ← коммитится
   │            ┌───────────┴───────────┐
   ▼            ▼                       ▼
 договор     frontend/ (React)     backend/ (Express)
 по нему    клиент по контракту    zod-валидация по контракту
 пишут обе стороны
```

### 3.1 Простыми словами: как всё устроено

Представим ресторан. **Контракт** — это меню: что можно заказать, что
получишь в ответ. Меню согласовано заранее и висит на стене
(`contract/dist/openapi.yaml`); повар и официант учат его, а не друг
друга. **Фронтенд** — зал: красивая витрина, где гость выбирает блюдо
(тип встречи), смотрит свободные столики (слоты) и делает заказ (бронь).
**Бэкенд** — кухня: принимает заказ, проверяет его по тому же меню
(zod: «email должен быть email»), смотрит в учётную книгу и отвечает
«принято» или «столик занят». **SQLite** — та самая учётная книга: один
файл `backend/data/app.db`, две страницы — «типы встреч» и «брони».
**Docker** — фургон: кухня, зал и книга упакованы в один ящик, который
открывается на любой машине одинаково. **CI** — санитарный врач: при
каждом изменении перепроверяет, что меню, кухня и зал не разошлись.
**Релиз с тегом** — номер партии на ящике (см. §6.2).

Теперь одним глазком — что происходит, когда гость жмёт
«Подтвердить запись»:

1. React берёт выбранный слот из состояния страницы и шлёт
   `POST /api/bookings` с телом `{eventTypeId, start, name, email}`
   (`frontend/src/api/client.ts`);
2. в dev запрос поймает Vite и перенаправит на бэкенд (`/api` →
   `VITE_API_TARGET`), в проде фронт и API живут на одном порту — запрос
   никуда не идёт, его принимает тот же Express;
3. бэкенд прогоняет тело через zod (лишние поля = отказ), проверяет, что
   тип существует (404), что слот из сегодняшней сетки и не в прошлом
   (400), считает конец времени `end = start + длительность` — клиенту
   верить нельзя, считает сервер;
4. в одной транзакции SQLite: нет пересечений с существующими бронями —
   вставляем, есть — 409 «Слот уже занят» (две вкладки, два клика —
   пройдёт ровно один);
5. ответ прилетает JSON'ом; на 201 фронт показывает экран успеха, на
   409 — ошибку и ссылку «Обновить слоты», сетка перезапрашивается и
   занятый слот становится некликабельным.

Три «слоя правды» проекта, и все они связаны контрактом: **что обещано**
(openapi.yaml), **как обещано** (спека api-contract.md с правилами и
E-кейсами), **что сделано** (код фронта и бэка + тесты, которые это
доказывают). Когда что-то из трёх расходится — CI или ревью это ловят,
а не надежда на аккуратность.

И технически, и физически это один процесс: в проде Express раздаёт и
API (`/api/*`), и собранную SPA-статику `frontend/dist` с SPA-fallback —
один порт, один контейнер, никакого CORS. В dev вместо бэкенда фронт
может работать на стабе контракта, а может на реальном бэкенде —
переключение одной переменной окружения.

Монорепо на npm workspaces: `contract`, `frontend`, `backend` — общий
lockfile и CI; `e2e/` намеренно вне workspaces (отдельная установка,
браузерные зависимости не смешиваются с прикладными).


## 4. Решения и почему

Формат каждого пункта: задача → что отвергнуто и почему → что выбрано →
чем это дорого (честная цена).

### 4.1 Контракт: TypeSpec → OpenAPI, а не руками и не из кода

**Задача.** Зафиксировать поведение так, чтобы фронт и бэк можно было
писать параллельно и не разъезжались.

**Отвергнуто.** Писать `openapi.yaml` руками — он неизбежно расходится с
кодом: нет механизма, который это проверит. Code-first (генерировать
контракт из Express/zod) — нарушает условие курса «сначала спецификация»:
контракт становится отчётом о реализации, а не договором.

**Выбрано.** TypeSpec — типизированный язык описания HTTP-API из
экосистемы Microsoft; эмиттер даёт OpenAPI 3.0 (артефакт `openapi: 3.0.0`).
Компортируется с
`--warn-as-error`, артефакт коммитится, а CI-проверка `contract-sync`
(compile → diff файла) не даёт артефакту устареть.

**Чем дорого.** Три пробела спецификации нашлись не при чтении, а при
реализации — каждый закрыт циклом «правим спеку → правим контракт →
синхронизируем issue»: код `duplicate_id` (для 409 «id занят» не было
кода), `server_error` (требование «все 5xx — модель Error» было
невыполнимо с закрытым enum), `@multipleOf(5)` (оказалось, выразим через
доп. библиотеку `@typespec/json-schema`, а не только комментарием).
Урок записан в память проекта: спецификации проверяют кодом.

**Грабли инструмента** (TypeSpec 1.15): объектные значения — `#{…}`;
обёртки ответов — `model X extends Response<404>`, форма `is` не принимает
`statusCode` в примерах; строковые коды — alias-union, а не enum
(кавычные литералы к members enum'а не присваиваются); относительный
`servers.url` Prism игнорирует. Всё это — в `learnings` памяти.

### 4.2 Dev-окружение: контейнер node:24 вместо локального Node

**Задача.** Работоспособная среда разработки в WSL, где Linux-`node`
отсутствует (есть только Windows-обёртка npm), а файлы лежат на DrvFs
(`/mnt/e`) — медленном и с чужими правами.

**Выбрано.** `docker-compose.dev.yml` с образом `node:24` и volume на
проект; все команды — через обёртку `./scripts/dev.sh <команда>`
(`dev.sh` — тоже артефакт среды: с её же помощью собираются артефакты).
Дополнительный бонус: dev-контейнер = база прод-образа, нативные модули
(лучше всех заметный `better-sqlite3`) ведут себя одинаково.

**Чем дорого.** Переменные окружения доходят до контейнера только если
они объявлены в compose (`PORT=${PORT:-}` и т. д.); пустая строка — это
не «не задано», поэтому везде `||` вместо `??`. Прерванные прогоны
оставляют осиротевшие контейнеры, занимающие порты host-сети.

### 4.3 Фронтенд: Vite + React + TypeScript + shadcn/ui, тонкий fetch-клиент

**Задача.** Шесть экранов, один источник данных, сборка — статика для
отдачи тем же Express.

**Отвергнуто.** Next.js/SSR — серверная рендеризация не нужна (демо за
одним портом, SEO не в приёмке), зато ломает простоту Docker и adds
рантайм-зависимость от Node для фронта. TanStack Query — слой кэша/отписок
при 2–3 запросах на переход; генератор клиента из OpenAPI — лишняя
сборочная стадия и магия в diff'ах.

**Выбрано.** Vite (8.x) + React 19 + TypeScript; shadcn/ui — компоненты
не библиотечные, а скопированные в репозиторий (полный контроль стилей,
Tailwind v4); react-router для шести маршрутов; клиент — ~60 строк
типизированного `fetch` (`src/api/`), типы вручную зеркалят контракт.
Расхождение поймает не вера, а prism-proxy (см. 4.6).

**Стаб вместо Prism для разработки (шаг 2.1b).** Prism — мок без
состояния: на нём не показать «забил слот → он стал Занято → повтор
дал 409». Поэтому `contract/mock-server` — маленькая in-memory
реализация всех пяти ручек со своей сеткой и пересечениями; его smoke
(46 проверок) повторяет E-кейсы спеки — фронт проверяется об честный
дубль, а не об заглушку.

**Переключатель реальности.** `VITE_API_TARGET=http://localhost:3001` —
и фронт идёт против настоящего бэкенда; правки кода нет.

### 4.4 Бэкенд: Express 5 + zod + SQLite (better-sqlite3)

**Задача.** Пять ручек, транзакционная занятость, один файл данных.

**Отвергнуто.** Nest/Fastify — лишний каркас ради пяти маршрутов;
Postgres — внешний сервис против условия «всё в одном контейнере» и
бесплатному тарифу; ORM — при двух таблицах только слой неопределённости.

**Выбрано.** Express 5 (дефолтный выбор курса), zod 4 для входа
(`.strict()` — неизвестные поля = 400, как требует sealed-схема
контракта), `better-sqlite3`: синхронный драйвер → проверка пересечений и
вставка в одной транзакции без гонок внутри процесса; файл `backend/data/app.db`
(весь каталог в gitignore — там PII и WAL-соседи).

**Ключевые детали, каждая — результат ревью:**

- **Канонизация времени.** Колонки `start/end` — TEXT, сравнение
  лексикографическое; «2026-09-10T09:30:00Z» и «…+03:00» рядом с
  «….000Z» врут. Всё входящее проходит `toIsoUtc` на границах
  репозитория; заодно бросает `InvalidDateError` с именем значения.
- **`now()` — единственный источник времени** (`services/now.ts`): env
  `NOW` фиксирует «сейчас» для тестов, сервисы принимают `nowFn`
  параметром; проверка перехода часовых поясов (MSK = +03:00 с 2014)
  закреплена тестом, сверяющим константу с Intl.
- **E3 раньше E5.** «Страница висела до полуночи» — старт вчера: дата
  формально вне окна, но ответ обязан быть «время слота уже прошло»
  (тот же код `slot_out_of_window`, другое сообщение): фронт по нему
  рефрешит сетку, а не подсказывает про дату.
- **seed идемпотентен** (`ON CONFLICT(id) DO NOTHING`): диск Render
  эфемерен, рестарт = чистый файл; каталог обязан появиться снова, а
  чужие (созданные владельцем) типы сид не перетирает.

### 4.5 Ошибки: одна модель на весь API

Все ответы `/api/*` с 4xx/5xx — только `Error {code, message}` (C7):
единый middleware в конце цепочки превращает `HttpError`, ошибки zod,
`InvalidDateError`, доменные ошибки слотов, переполненное тело (413) и
даже необработанные исключения (500, с логом на сервер) в JSON нужной
формы. Неизвестный `/api/*` — 404 в той же форме: SPA-fallback
настроен только на не-`/api` GET, а пути, похожие на файлы (`*.js`),
fallback не получают index.html — классическая ловушка SPA закрыта.

### 4.6 Тесты: слои

Слой обязателен этапу — без тестов задача не считается законченной.

| Слой | Что | Где бегает |
|---|---|---|
| контракт | `tsp compile --warn-as-error`; Prism-smoke (27 проверок: все ручки/коды, 404/409 через `Prefer: code=NNN`) | локально + CI `contract-sync` |
| стаб | smoke 46 проверок: стейтфул-сценарий, E-кейсы | локально |
| бэкенд | vitest 72: хранилище, слоты, HTTP (E1–E20), сверка ответов с OpenAPI через `prism proxy` (с grep лога Violation — сам прокси нарушения ответов статусом не карает) | локально + CI `E2E` (job `checks`) |
| фронт | typecheck + oxlint + production build | локально + CI |
| e2e | Playwright 9 сценариев против реальных бэкенда+фронта (webServer), включая «Занято», stale-tab 409 и двойной клик | локально + CI `E2E` |
| релиз | release-please: semver из Conventional Commits, CHANGELOG, тег + GitHub Release | CI при push в main |

Отдельная история — **почему e2e в CI на `node:24`, а не на официальном
mcr-образе Playwright**: в `node:24.20.0` есть тулчейн сборки нативных
модулей (`make` для `better-sqlite3`), и это же образ dev-обёртки и
прод-сборки — одна среда везде, без расхождения «на runner'е / дома».
Критерий «CI ловит поломку» доказан циклом: зелёный → коммит со
сломанной ассертой → красный → откат → зелёный.

### 4.7 Git-процесс

Каждое существенное изменение — ветка `<тип>/<тема>` от `main`
(например `feat/backend-api`), внутри — коммит-чекпоинты в формате
Conventional Commits (это кормит release-please, а не эстетика). Пуш и
мерж — за владельцем; сопровождение PR — за агентом: поллинг проверок,
триаж **каждого** замечания ревью (исправить коммитом или возразить в
комментарии с причиной), пересборка и перепроверка локально. За курс —
19 PR, ~50 раундов ревью; замечания бота ловили реальные дефекты
(гонка двух параллельных прогонов на один workspace runner'а,
полупустая проверка ответов, E3-порядок), а не только стиль.

### 4.8 Docker и Render

**Образ.** Multi-stage: сборка на `node:24.20.0` (npm ci → vite build →
tsc → `npm prune --omit=dev`), runtime — `node:24.20.0-slim`, итого
~103 МБ. Пины точные до патча: плавающий `node:24` уже успел разойтись
(локально 24.20.0, в CI 24.18.1). `HEALTHCHECK` зондирует контрактную
`GET /api/event-types` — лишних ручек ради мониторинга не заводим
(контракт = ровно пять). `CMD` — один процесс на `PORT`.
`.dockerignore` отсекает секреты, базы и node_modules из контекста.

**Площадка.** Render (вариант A из `docs/deploy-global.md`): сборка из
Dockerfile, `PORT` подставляет платформа (у нас вышел :10000 — приложение
читает env, совпадение с `ENV PORT` образа не обязательно), free-тариф.
Осознанные следы тарифа: диск эфемерный — после рестарта брони обнуляются,
seed пересоздаёт типы (принято решением §11.10 курса); простой сервиса
«засыпается», первый запрос — 30–60 секунд. Живое демо с сохранением
данных и своим доменом — вариант B (VPS + Docker volume + Caddy), тот же
образ, описан в гайде.

**Принято позже:** образ работает от non-root — `USER node` в `Dockerfile`
(поставлен ревью-правкой, образ пересобран и проверен: запись БД, рестарт,
health). Оговорка про площадку: с non-root в volume хоста должен быть uid 1000
(обычный пользователь Linux/WSL), иначе запись в смонтированный каталог
упрётся в права — это актуально для варианта B (VPS + Docker volume), на
free-тарифе Render volume нет.

## 5. Как запустить

Все команды — из корня; в WSL без Linux-Node — через обёртку
`./scripts/dev.sh` (она же `docker compose -f docker-compose.dev.yml run
--rm dev …`).

### 5.1 Фронтенд без бэкенда (на стабе контракта)

```bash
./scripts/dev.sh npm install                              # один раз
./scripts/dev.sh npm run start -w @cal-com/mock-server    # стаб :4020
./scripts/dev.sh npm run dev -w frontend                  # http://localhost:5173
```

### 5.2 Полный стек в dev

```bash
PORT=3001 ./scripts/dev.sh npm run dev -w backend         # API + seed
VITE_API_TARGET=http://localhost:3001 ./scripts/dev.sh npm run dev -w frontend
```

### 5.3 Прод локально (один порт)

```bash
./scripts/dev.sh sh -c 'cd frontend && npm run build'
./scripts/dev.sh sh -c 'cd backend && npm run build'
```

## 6. Публичный стенд и релиз

### 6.1 Стенд

- Демо: публичный адрес на Render настраивается, URL фиксируется в README
  и `docs/deploy-global.md` после первого деплоя.
- Релиз: тег `cal-com-v1.0.0` + GitHub Release, CHANGELOG собирается из
  Conventional Commits автоматически (release-please).

### 6.2 Теги и релизы: как это устроено, без магии

**Уровень git.** Тег — это именованный закреплённый указатель на
конкретный коммит (в отличие от ветки, он никуда не «едет»). Тег
`cal-com-v1.0.0` — метка: «вот этот коммит main — версия 1.0.0».
Существуют теги локально и на сервере: `git push origin v1.0.0` — это
просто отправка метки, сам коммит уже там.

**Уровень GitHub.** «Release» — веб-объект поверх тега: заголовок,
сформированный CHANGELOG, кнопка просмотра diff между версиями. Тег без
release — просто метка; release без тега не бывает.

**Уровень семантики: Conventional Commits.** Причина, почему весь проект
коммитился в формате `feat:` / `fix:` / `BREAKING CHANGE` — не эстетика:
это машиночитаемая история. Из неё автоматически выводится, какая версия
следующая: хотя бы один `feat:` → минор (`0.1.0 → 0.2.0`), только `fix:`
→ патч (`0.2.0 → 0.2.1`), `BREAKING CHANGE` / `!` → мажор
(`0.2.1 → 1.0.0`). До релиза 1.0 действовало правило
`bump-minor-pre-major`: `fix:` тоже поднимал минор, потому что у
нулевой версии патч-релизов фактически не бывает.

**Уровень автоматизации: release-please.** Механика в трёх файлах:

| Файл | Роль |
|---|---|
| `.github/workflows/release-please.yml` | запускать экшен на каждый push в `main` |
| `release-please-config.json` | стратегия: тип релиза (`node`), правила bump'а, какие файлы править |
| `.release-please-manifest.json` | **текущая версия** — источник истины для following расчётов (`"." : "1.0.0"`) |

Что делает экшен при каждом push в main:

1. читает manifest (текущая версия) и находит последний release-PR;
2. собирает все коммиты `main` с момента прошлого релиза;
3. считает следующую версию по Conventional Commits;
4. создаёт (или обновляет — он кумулятивный) **release-PR**: ветка
   `release-please--branches--main--...`, в ней bump версии в
   `package.json`/lock и перегенерированный `CHANGELOG.md`;
5. пока release-PR не влит, ничего не релизится — **релиз — это мерж
   одного человека**, осознанный «курсор» в истории.

Когда release-PR влит (у него заголовок `chore(main): release …` — это
маркер для экшена), тот же workflow во второй раз видит main и:
создаёт аннотированный тег (отсюда префикс `cal-com-` — имя компонента в
конфиге, чтобы в монорепо разные пакеты не сталкивались тегами) и
публикует GitHub Release с CHANGELOG. Всё — ни одного ручного тега.

**Как это выглядело в нашем проекте (факты).** #14 — конфиг и workflow
(с тегом ошиблись: `@v17` — версия core-библиотеки, а у *экшена* своя
линейка, нужен `@v5`; поймали по логу упавшего прогона, починили в #15).
Дальше GitHub отбивал экшену создание PR — пока не включили переключатель
Settings → Actions → «Allow GitHub Actions to create and approve pull
requests». После rerun: release-PR #18 (автокоммит с bump'ом 0.0.0 → 1.0.0
и CHANGELOG из ~50 наших коммитов) → мерж → тег `cal-com-v1.0.0` +
Release. Проверить глазами: `git fetch --tags && git show cal-com-v1.0.0`
и вкладка Releases.

**Как сделать то же самое руками** (полезно для понимания, в проекте не
требуется):

```bash
git tag -a cal-com-v1.0.1 -m "patch release"   # аннотированный тег на HEAD
git push origin cal-com-v1.0.1                 # отправить метку
gh release create cal-com-v1.0.1 --generate-notes   # release с автозаметками
```

release-please ровно это делает сам, но из истории коммитов, а не из
ручного нажатия.

### 6.3 Что проверить руками после чтения гайда

1. `git log --oneline -20` — все коммиты в Conventional-формате;
2. вкладка Releases — тег v1.0.0, CHANGELOG, diff с «previous»;
3. `.release-please-manifest.json` — версия 1.0.0;
4. Actions → «Release please» — зелёные прогоны на push в main;
5. PR #18 — как выглядит «кумулирующий» релизный PR до мержа.
