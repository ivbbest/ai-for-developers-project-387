# Гид по решениям: ИИ-агент в GitHub-процессе этого репозитория

Документ для тех, кто не присутствовал при настройке: зачем в репо четыре
opencode-воркфлоу, почему они устроены именно так и какие ограничения
проверены фактами, а не ожиданиями. Парный документ —
`docs/project-context.md` (что за проект); продуктовые решения перенесённого
приложения — `docs/decision-guide.md` (наследие предшественника).

## 1. Модель процесса

Предмет репозитория — не рост продукта, а след: **каждая существенная работа
оставляет в GitHub проверяемый артефакт** (прогон Actions, ответ в треде,
коммиты в PR, релизный тег). Отсюда три принципа, влияющие на все решения ниже.

1. **След = ссылка.** Пункт плана считается сделанным по URL прогона/PR/коммита
   или SHA, не по «должно работать».
2. **Анти-петля важнее удобства.** Агент, отвечающий на собственные ответы,
   сжигает ключ и тонет в собственном шуме. Каждый интерактивный воркфлоу
   спроектирован так, чтобы комментарий бота не порождал новый прогон, — и
   это проверяется операционно (список прогонов за 2 минуты после ответа),
   а не чтением условия `if:`.
3. **Права — по минимуму, модель — по задаче.** Write-разрешения GITHUB_TOKEN
   выдаются только там, где воркфлоу сам создаёт артефакты токеном; комментарии
   пишет GitHub App по OIDC (нужен только `id-token: write`).

## 2. Четыре воркфлоу

| Файл | Событие | Модель | Назначение |
|---|---|---|---|
| `opencode.yml` | `issue_comment`, `pull_request_review_comment` (created) | big-pickle | Интерактив: ответ по команде `/oc`/`/opencode` в треде issue или в строке diff |
| `opencode-triage.yml` | `issues` (opened) | big-pickle | Автотриаж нового issue: причина · модули · путь, ответ комментарием |
| `opencode-review.yml` | `pull_request` (opened, synchronize, reopened, ready_for_review) | big-pickle | Авторевью человеческих PR с критериями (контракт, edge-кейсы, типы, стиль, тесты) |
| `opencode-schedule.yml` | `schedule` (`0 3 * * *` UTC) + `workflow_dispatch` | big-pickle | Ночная проверка деплоя: Lighthouse → markdown-отчёт → issue с меткой `perf-report` |

Общие элементы всех четырёх: пин экшена `anomalyco/opencode/github` на SHA
актуального релиза (v1.18.29) и `actions/checkout` на SHA v7.0.1;
`persist-credentials: false`; job-level `timeout-minutes` (60 у интерактива,
20 у остальных — у самого экшена параметра timeout нет); `concurrency` с
`cancel-in-progress: false` (вызовы по одному треду не накладываются, но и
очередь не отменяют); `share: false` (публичный репозиторий, сессии наружу не
нужны); ключ провайдера — только `${{ secrets.OPENCODE_API_KEY }}`.

## 3. Решения и их цена

### 3.1 Модель единообразно `opencode/big-pickle`

Все четыре воркфлоу на одной модели. Аргумент: задачи курса (разбор треда,
ревью диффа, анализ JSON-замера) укладываются в неё; вариативность моделей
добавила бы переменную там, где и так отлаживается процесс. Цена: на больших
PR разбор медленнее, чем на флагманской модели; для демо-нагрузки (проект
учебный) это осознанно. `variant`/`agent` не используются (YAGNI).

### 3.2 Интерактив: двухуровневый фильтр вызова

Первичный — параметр `mentions: /oc,/opencode`: экшен сам ищет команду в
тексте комментария. Вторичный — job-level `if:`: автор ровно `ivbbest`
(владелец учебного репо, круг вызывающих ограничен), автор не бот, и текст
содержит команду.

Третье условие появилось не из плана, а из факта: первый вариант `if:` фильтровал
только автора — обычный комментарий владельца без команды доходил до экшена,
тот падал с «Comments must mention /oc», и в Actions светился красный прогон
(run 33950455803). Экшен при отсутствии mention ошибается, а не скипает;
проверка команды переехала в условие (PR #8). Вывод общего вида: **фильтр
события должен отсекать шум до запуска экшена, иначе «красный X» становится
частью рабочего процесса**.

### 3.3 Триаж: guard из трёх условий + возраст аккаунта

`issues` в GitHub — это и PR (PR технически issue): без `!issue.pull_request`
триаж комментировал бы каждый pull request. `user.type == 'User'` отсекает
ботов и собственный App — issue от ночного воркфлоу не получит двойного
разбора. Возраст аккаунта ≥30 дней (github-script) — шум от свежих
спам-регистраций. `workflow_dispatch` намеренно нет: у ручного запуска нет
issue-контекста, prompt не к чему применять; ручной повтор — `/oc explain`
в треде.

Prompt — по требованию курса, фиксированный («причина · затронутые модули ·
путь, ответь комментарием, код не менять»): у события `issues` комментария нет,
без prompt агент не знает, чего хотеть.

### 3.4 Авторевью: человеческие PR, токен раннера

Фильтр `pull_request.user.login == 'ivbbest'`: агентские PR (`opencode/*`)
ревьюит человек — иначе замечания агента разбирал бы сам агент (двойной проход
по каждому PR и лишний расход). Режим замечаний — `use_github_token: true`
(комментарии от имени `github-actions[bot]`), не App-режим.

Факт, стоивший итерации: экшен **не подхватывает GITHUB_TOKEN сам** — без
явного env шаг падает («GITHUB_TOKEN environment variable is not set»,
run 33951997871); и публикация review-комментариев требует `pull-requests:
write` — read-вариант D4 не пережил первую же попытку написать. Оба подъёма
задокументированы why-комментариями в файле.

Ещё один неочевидный факт платформы: для `pull_request`-событий YAML берётся
из **head-ветки PR**. Воркфлоу, замерженный в main после открытия PR, на этот
PR не действует вовсе — ни прогона, ни skipped (так PR #15 не попал под
авторевью, созданное в #14).

### 3.5 Расписание: guard, warm-up, дедуп

Cron `0 3 * * *` (06:00 МСК) — не чаще раза в сутки; `workflow_dispatch` рядом
для проверки без ожидания ночи. Порядок шагов — «сырые данные собирает обычный
CI-шаг, агент превращает в выводы»: guard `APP_URL` (пустая переменная →
красный прогон с внятной ошибкой, а не «зелёный мусор»), warm-up curl с
ретраями (Render free-tier холодный 30–60 с), Lighthouse CLI → `report.json`,
и только потом prompt агента: анализ, `perf-report.md`, issue с меткой
`perf-report`. Дедуп: открытый issue с меткой обновляется комментарием, новый
не создаётся — иначе ночной отчёт плодит новые issue каждую ночь.

Правка по ревью: Lighthouse с `continue-on-error` + ветка prompt «замера нет —
сообщи в issue, не выдумывай». Иначе site-down прерывал job до агента, и
утренний читатель видел красный прогон без объяснений; с правкой сбой
превращается в сигнал.

Права — четыре write (`contents`, `pull-requests`, `issues`, `id-token`):
воркфлоу сам создаёт артефакты (issue/комментарий). Это единственные права на
запись среди четырёх; интерактив и триаж живут на OIDC+App.

### 3.6 Анти-петля: доказательство списком прогонов

Критерий операционный: после ответа агента **нет нового выполненного прогона
того же воркфлоу на тот же тред в течение 2 минут**; доказательство — `gh run
list`, а не чтение `if:`. Skipped-прогоны на комментарии бота — штатный шум
(job не выполняется, ключ не тратится), не петля. Проверено: интерактив
(ответ в #6 → skipped 33950038397), триаж (комментарий в #12 → новых прогонов
нет), авторевью (пишет review/comment-события, которых в `on:` нет).

При обнаружении петли: попросить владельца отключить workflow в Actions →
исправить условие → включить → повторить тест; случай — в lessons.

### 3.7 Релизный цикл и Conventional-заголовки

release-please продолжает работать с перенесённым кодом: manifest 1.0.2,
CHANGELOG не переносился (собрался заново с v1.0.3). Факт, стоивший цикла:
squash-мерж пишет в main **заголовок PR** как сообщение коммита — PR #15 с
заголовком «Email limit fix done…» release-please не увидел (`No user facing
commits`), релиз открылся только после следующего PR с Conventional-заголовком
(#16 `fix: …` → release-PR #17 → тег `cal-com-v1.0.3`). Правило: заголовок
каждого PR, который должен попасть в CHANGELOG, — Conventional.

PR, созданный ботом (`github-actions[bot]` — release-please), получает прогоны
в статусе `action_required`: GitHub требует явного одобрения maintainer'а,
публичного API для approve нет — только UI. Это единственная обязательная
ручная операция в цикле.

### 3.8 Установка App и ключ

GitHub App (opencode-agent) расширяется на репозиторий вручную (Configure →
Add repository), а не мастером `opencode github install`: мастер генерирует
свой `opencode.yml` (`@latest` без пинов, без фильтра автора, `share` по
дефолту) — всё то, от чего мы защищаемся. Ключ провайдера — только в секретах
репозитория (`OPENCODE_API_KEY`); в файлах воркфлоу — только имя переменной.
Значения секретов не читаются, не пишутся и не логируются.

## 4. Известные ограничения (проверено фактом)

- Экшен при комментарии без команды (mentions не совпали) завершается ошибкой,
  не скипом → фильтр команды обязателен в `if:` (см. 3.2).
- YAML `pull_request`-воркфлоу берётся из head-ветки PR (см. 3.4).
- Ботовые PR: одобрение прогонов только в UI (см. 3.7).
- `/oc review` **после** squash-мержа с удалением ветки бесполезен: checkout не
  находит ref. Ревью в трееде — строго до мержа.
- `gh pr edit` падает на GraphQL-депрекации Projects classic; обход — REST
  `gh api --method PATCH /repos/…/pulls/N -f body=…`.
- У экшена нет параметра `timeout` — только job-level `timeout-minutes`.
- Пинов на теги нет нигде: все actions запинены на SHA актуальных релизов;
  при аудите сверять с `gh release list`.
