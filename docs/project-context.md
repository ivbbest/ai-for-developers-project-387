# Проект «Календарь звонков (продолжение)»: контекст и границы

Документ для тех, кто открывает это репозиторий впервые и не был при разработке
предшественника. Он отвечает на вопросы «что здесь вообще происходит и зачем»:
продукт перенесён из другого репозитория, а вся активность этого — про процесс.

## 1. Что это за проект

Учебный проект курса «ai-for-developers» (Хекслет): продолжение «Календаря
звонков» — репозиторий-предшественник `ai-for-developers-project-386` довёл
приложение до релиза v1.0.2 (контракт, фронт, бэк, e2e, Docker, CI/CD, демо
на Render). Здесь начинается второй предмет: **интеграция ИИ-агента в
GitHub-процесс команды**. Правила такие: агент работает внутри репозитория —
отвечает в issue по команде, разбирает новые задачи автоматически, открывает
pull request, вносит правки после ревью и выходит по ночному расписанию.
Продуктовая функциональность при этом не растёт: приложение перенесено готовым,
а изменения — только те, что демонстрируют цикл «жалоба → разбор → PR → ревью →
релиз».

Контроль качества в курсе специфический: «тестом» каждого шага является
**видимый след в GitHub** — прогон Actions, ответ агента в треде, коммиты в PR,
артефакт отчёта, релизный тег. «Должно работать» не засчитывается; засчитывается
ссылка.

## 3. Предметная область приложения

Кратко, детали — в перенесённых `docs/project-understanding.md` и
`docs/decision-guide.md` (они описывают продукт так, как он задумывался в 386):

- сервис бронирования звонков по мотивам Cal.com, без авторизации;
- владелец публикует типы встреч, гость выбирает слот и бронирует (имя, email,
  заметки);
- Design First: контракт TypeSpec → OpenAPI — источник правды, фронт и бэк
  независимо; SQLite, один прод-порт, Docker multi-stage;
- времени в сутках: сетка слотов в Europe/Moscow, занятость атомарна
  (транзакция, 409 при гонке).

Единственное продуктовое изменение, сделанное здесь, — исправление бага
«длинный email» (лимит 254 объявлен в контракте, форма показывает предел,
отказ называет число) — выполнено агентом по циклу шагов 3–4, релиз v1.0.3.

## 4. Входной сценарий курса (6 шагов)

1. **Перенос** — репозиторий 386 берётся целиком, автотест зелёный, плюс план
   развития (≥1 фича, ≥1 баг; записи — жалобы пользователей без готовых
   решений): `docs/development-plan.md`.
2. **Установка агента** — GitHub App + интерактивный воркфлоу: ответ по команде
   `/oc` в комментариях к issue и к строкам diff в PR.
3. **Issue и триаж** — два способа позвать: команда в треде (агент читает всю
   историю) и автотриаж новых issue по фиксированному prompt.
4. **От issue к PR и ревью** — `/oc fix` ведёт ветку и открывает PR; замечания
   через оба канала комментариев; авторевью на PR; релизный цикл release-please.
5. **Расписание** — ночная проверка деплоя (Lighthouse + анализ), результат —
   артефакт прогона и issue по находкам.
6. **Финальная проверка** — процесс предсказуем: триггеры, права, расходы,
   круг вызывающих — сведены в таблицу README.

## 5. Роли

- **Владелец репозитория (человек)** — секреты и настройки репозитория,
  деплой, одобрение прогонов от ботов (платформенное ограничение UI), финальное
  слово в спорных ревью-вопросах.
- **Локальный агент** — ведёт ветки, PR, реестр задач и память проекта;
  мержит после зелёных проверок и разбора замечаний.
- **Агент в GitHub Actions** (тот же инструмент, другие права — GitHub App) —
  отвечает в тредах, триажирует, правит свои PR, готовит ночные отчёты.
  Границы его заданы условием в каждом воркфлоу (см. `agent-decisions.md`).
