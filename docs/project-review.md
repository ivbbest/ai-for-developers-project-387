## Рекомендации

### Р1. Дописать критерии приёмки в issue #12 до начала работ

В #12 есть триаж-разбор, но нет формулировки «исправлено, когда…» (это
зафиксировано как задача 4.12). Почему: без измеримой формулировки fix
не проверить объективно, а правило проекта «след = ссылка» требует проверяемого
результата; записать критерии до `/oc fix`.

### Р2. Закрыть issue #6 как разведанный

Ответ получен в issue #6 (разбор по файлам), новых вопросов нет — вопрос
закрыт. Почему: открытый issue без владельца — шум в списке; закрытие сохраняет
реестр открытых задач честным.

### Р3. Определить судьбу issue #25 (perf-report)

Цель-критерий зафиксирован («Performance ≥ 0.9, TBT < 200 мс, повторный
замер»), но работы по исправлению не назначено. Почему: цель без назначенной
задачи либо висит вечно, либо закрывается как мониторинг. Механизм «повторный
замер» уже есть — ночной crон; после двух зелёных замеров issue можно закрыть
по цели, до этого — держать открытым как источник данных.

### Р4. Страховать чистоту рабочего каталога в расписании, а не список имён

`.gitignore` закрывает три известных имени. Пост‑обработка агента может
создать произвольный файл — следующий мусорный PR будет с другим именем.
Почему: запрет в prompt не сработал дважды (факты #23, #26) — prompt задаёт
намерение, а пост‑обработку делает экшен. Надёжный гейт — шаг после
`Run opencode report`: `git status --porcelain` пуст, иначе fail с внятным
сообщением. Это фикс причины, а не симптома конкретного файла; в сочетании
с PR #30 полностью закрывает класс «агент открыл PR с отчётом».

### Р5. Убрать из текста ошибки guard'а APP_URL ссылку на внутренний реестр

Сообщение «задача 1.6 реестра» в `opencode-schedule.yml` — отсылка к
внутреннему чек‑листу проекта в публичном логе прогона. Почему: репозиторий
публичный, лог читают не только участники; текст должен быть самодостаточным
(«APP_URL не задана: Settings → Secrets and variables → Actions → Variables»).

### Р6. Добавить в интерактивный prompt требование отвечать без иноязычных вставок

В комментарии агента в PR #30 встретилась вставка «по工作机制» (символы CJK) —
артефакт модели в публичном треде. Почему: тред — витрина процесса, и одна
строка в prompt (отвечай по-русски, без вставок на других языках) закрывает
класс. Правка в `opencode.yml` — одна строка, эффект — гигиена видимой части.

### Р7. Мелочь: `issues: read` в opencode-review не используется

Ревью пишется токеном раннера (`pull-requests: write`), чтение issues не
задействовано. Почему: права держатся минимальными по шагу 6; к удалению
не срочно, но при следующей правке воркфлоу строку стоит убрать.

### Р8. Наблюдение: сдвоенный комментарий «ревью пройдено» на PR #30

Один прогон авторевью оставил два одинаковых по смыслу комментария. Prompt уже
просит «одним комментарием» — остаётся как известное ограничение модели, на
процесс не влияет.

### Р9. Наблюдение: `docs/project-context.md` называет файл правил в таблице

Строка «Правила проекта и команды CI-гейта» указывает на файл правил
локального агента — это внутренняя инфраструктура, которой в публичном
документе быть не должно. По правилам гигиены проекта такие ссылки выносятся
только в учебные planning-доки курса; заменить на нейтральное описание
(«правила локального агента»). Косметика, не блокер.
