## Проблемные места и рекомендации

### Р1. SDD-цикл из правил проекта не отработан для пунктов плана развития

Файл правил (AGENTS.md, раздел «SDD (лайт)») требует: для каждой фичи/бага
из плана развития — спека в `docs/specs/` по циклу «Issue → спека → план →
код → проверка → обновить специю». В `docs/specs/` лежат только `TEMPLATE.md`
и `api-contract.md`; **спеки по багу 1 (длинный email) и фиче 1 (отмена брони)
не создавались**. Баг 1 закрыт через issue #10 и PR (#15/#16) без спеки; фича
1 ждёт своего цикла (issue #12 — кандидат).

**Почему важно:** правило зафиксировано именно затем, чтобы задача понималась
без пересказа и имела измеримый критерий приёмки; без спеки цикл «от обсуждения
к коду» теряет след, а следующий агент/читатель вынужден восстанавливать
контекст из треда.

**Что сделать:** при старте цикла по фиче 1 (отмена брони) завести
`docs/specs/cancel-booking.md` по шаблону `TEMPLATE.md` (Цель, критерии
приёмки, ограничения, статус). Для бага 1 — задним числом зафиксировать спек
в `docs/specs/email-limit.md` со ссылками на issue #10 и PR #15/#16, чтобы
правило SDD выполнялось для всех пунктов плана.

### Р2. Спека контракта не отражает лимит email — расхождение с планом развития

`docs/specs/api-contract.md:63` описывает поле email как `string (валидный)` —
без числа 254, хотя `docs/development-plan.md` (Баг 1, «Ожидаемое поведение»)
требует: «лимит email объявлен в описании API так же, как лимиты имени и
заметок». Технический контракт корректен (`contract/models.tsp` `@maxLength(254)`,
OpenAPI `maxLength: 254` — факт подтверждён), отстаёт только человекочитаемый
документ.

**Почему важно:** правка закрыла баг в коде и контракте, но документационная
часть требования из плана не выполнена; следующему читателю лимит придётся
искать в контракте, а не в спеке.

**Что сделать:** дополнить строку лимитом с указанием поведения (актуальная
валидация: максимум **254** символа; лимит проверяется по `trim`-значению —
см. `frontend`, `docs/specs/email-limit.md`).

---

### Р3. Perf-проблема из issue #25 имеет конкретную причину в сборке фронта

Локальный аудит кода подтверждает находку Lighthouse (unused JS 64 KiB, TBT
1010 мс, main thread 2.3 с): **нет покомпонентной загрузки роутов** —
`frontend/src/App.tsx` статически импортирует все семь страниц
(`import { AdminNewTypePage } from './routes/admin-new-type'` и т.д.), без
`React.lazy`/`Suspense`. Единственные тяжёлые зависимости (календарь
react-day-picker, сетка слотов, админка) грузятся на первую страницу.

**Почему важно:** цель в issue #25 («Performance ≥ 0.9, TBT < 200 мс»)
сформулирована, но без назначенной работы и без привязки к причине; ночной
cron будет лишь фиксировать замер. Route-level code-splitting — штатное
решение Vite и прямой ответ на «unused JS».

**Что сделать:** кандидат в следующий цикл: `React.lazy` по роутам
(календарь/сетка — самый заметный кандидат), повторный замер ночным cron'ом,
закрытие #25 по достижении цели. Работу вешать отдельной задачей/спекой,
а не прятать в шаг 6.

### Р4. Рассинхрон пинов `upload-artifact`: v4 в `e2e.yml`, v7.0.1 в `opencode-schedule.yml`

`e2e.yml:78` пинит `actions/upload-artifact@ea165f8d65b6…` (v4), а
`opencode-schedule.yml:132` — `@043fb46d1a93…` (v7.0.1). Оба — SHA, значит это
не уязвимость, но два разных major для одного действия — расхождение, которое
со временем превращается в «а почему тут старый?».

**Почему важно:** аудит шага 6 (6.1c) проверил только `opencode*.yml`, где все
пины актуальны; смежный workflow (e2e) из-под проверки выпал. Обновление v4→v7
меняет тред с mtime-наборами (потоковый upload); e2e-артефакт маленький — риска
нет, но прогнать e2e после синка обязательно.

**Что сделать:** поднять `e2e.yml` до v7.0.1 (тот же SHA, что в schedule)
и закрыть проверкой прогона E2E.

### Р5. `docs/reading-guide.md` устарел: статус застрял на шаге 1

Шапка путеводителя: «актуален на 2026-09-04 (шаг 1 — перенос кода — не
выполнен…)». Фактически перенос давно влит (шаг 1 закрыт 2026-09-04, шаги 2–5
— 2026-09-05, шаг 6 в процессе). Путеводитель — первое, что читает новый агент,
и его статус расходится с реальностью.

**Почему важно:** задача 6.11 прямо требует «финальный V-маршрут
reading-guide + закрытие ритуала памяти»; устаревшая шапка — часть этого хвоста,
плюс она вводит в заблуждение до выполнения 6.11.

**Что сделать:** в рамках 6.11 обновить статус и маршрут под фактическое
состояние (шаги 1–5 закрыты, ссылки на следы), подтвердить/освежить контрольные
вопросы.

### Р6. В удалённом репозитории три параллельных ревью-ветки и два открытых PR ревью

На remote сейчас существуют `docs/project-review` (PR #31),
`analysis/comprehensive-review` (PR #33) и добавляется эта рекомендательная
ветка. PR #33, кроме документа, несёт правки workflow и файла правил, которые
**уже слиты в main** через PR #32 (файлы байт-в-байт совпадают — сверено), при
этом тело PR утверждает «Существующие файлы не изменены (согласно запросу)».

**Почему важно:** три ревью-артефакта с пересекающимся содержанием — риск
двойного разбора одних замечаний, конфликтующих правок и размытого следа.
Ситуация разборчива, но дорого обходится в дальнейшем сопровождении.

**Что сделать:** явно развести зоны ответственности трёх документов (проект-ревью
— операционное состояние и его закрытие; comprehensive — стратегия и план
закрытия курса; этот аудит — инфраструктурные расхождения и код), после мержа
ненужные ветки закрыть, чтобы реестр веток не плодился.

### Р7. Локальная гигиена репозитория: локальный `main` отстаёт, мёртвые ветки висят

При аудите локальный `main` был позади `origin/main` на один коммит (PR #32 не
подтянут), а в remote остаются ветки-призраки `chore/migrate-app`,
`docs/scaffold-closure`, `ci/*` (SLAT, pr-migrate, review-hardening) и т.п.,
чей PR уже в main.

**Почему важно:** отсталый локальный `main` — источник ложных ревью-замечаний
(урок от 2026-09-05: комментарий «файла нет» оказался следствием устаревшего
base); ветки-призраки замусоривают поиск.

**Что сделать:** перед каждой новой веткой — `git fetch origin` и проверка
`git merge-base --is-ancestor origin/main HEAD`; после мержа PR — удалять
remote-ветку (владельцу; агент удалять не может по правилам).

### Р8. Наблюдение: сдвоенный комментарий и расширенные права ревью — известные ограничения

`opencode-review.yml` после эскалации D4 держит `pull-requests: write`
и явный `GITHUB_TOKEN` (причина зафиксирована why-комментарием). Признаков
злоупотребления нет; вариант урезать права до read при проверке, что ревью
всё ещё пишется, — оставлен на потом. Сдвоенный комментарий авторевью
и вставка «по工作机制» (CJK) в треде публичного PR — известные артефакты модели,
закрыты правилом языка в файле правил (Р6 `project-review.md` выполнен),
правки prompt могли бы дополнительно смягчить вставки в будущих прогонах.

**Что сделать:** не менять сейчас; при следующей правке воркфлоу — ревизия
прав (возможно вернуть к read) и явная строка в prompt «отвечай одним
комментарием, без вставок на других языках».

### Р9. Открытые issue: нет владельца у двух из трёх

После закрытия #6 (разведка) и #10 (баг email) в списке открытых остаются
#12 (отмена брони — фича из плана, критерии приёмки есть) и #25 (perf-monitoring).
У обоих нет назначенного исполнителя/срока, хотя планы развития определяют
следующую продуктовую работу.

**Почему важно:** открытый issue без назначения — «вечный TODO»; в публичном
репо это ещё и витрина: сначала читатель видит «не могу отменить бронь», не
видя плана.

**Что сделать:** завязать #12 на цикл SDD (спека → задача → `/oc fix`),
#25 — на Р3; определить явный срок ближайшего статус-апдейта (например, после
каждых двух ночных замеров).
