# AGENTS.md — «Календарь звонков (продолжение)»

Учебный проект Хекслета «ai-for-developers»: **интеграция работы агентов в GitHub-процесс
команды**. Репозиторий: https://github.com/ivbbest/ai-for-developers-project-387 (публичный).
Локальная папка: `/mnt/e/hexlet/cal-com-continue`.

Продолжение проекта «Календарь звонков» (репо `ai-for-developers-project-386`, локально
`/mnt/e/hexlet/cal-com`, релиз v1.0.2). Продуктовая функциональность здесь **не растёт**:
переносится готовое приложение, а дальше агент работает внутри GitHub — отвечает в issue,
разбирает задачи, открывает pull request, вносит правки после ревью, выходит по расписанию.
Проверяется процесс: следы работы (прогоны Actions, ответы в issue, PR с правками, отчёты)
должны быть видны в репозитории. Входной сценарий — `input/user-story.txt` (6 шагов).

Прочитай перед началом работы. Правила и факты — в файлах, а не в диалоге
(каждая сессия стартует с чистого контекста).

## Секреты и `.env` (НЕ читать)

- `.env` и секреты (API-ключи, пароли, токены) — **вне контекста**, считать несуществующими.
  Смотреть/менять/создавать может только пользователь; агент — никогда.
- **Запрещено** читать/подставлять/выводить/логировать значения секретов, писать их
  в файлы, коммиты, задачи, issues/PR. Допустимо знать только *имена* переменных
  (`OPENCODE_API_KEY`, `HEXLET_ID`, …); значения — никогда. Ключи в GitHub Secrets
  добавляет только пользователь.
- Ключ провайдера модели — **только** в секретах репозитория; в файлах воркфлоу его нет
  даже в приватном репо (остаётся в истории, придётся отзывать).

## Границы действий

> **Git-workflow (унаследовано от предшественника).** Каждая существенная разработка —
> **отдельная ветка от `main`** с именем `<тип>/<тема>`. Агент создаёт ветки, **коммитит
> в них** (чекпоинт на каждое существенное изменение). **Push ветки и открытие PR —
> пользователь** (в текущем окружении push агенту закрыт правилами). **Слияние в `main`,
> пуш в `main`, force-операции, удаление веток — только пользователь.**
> Оговорка: границы относятся к **локальному** агенту. Агент в GitHub Actions
> (шаги 2–5) работает правами GitHub App и по сценарию курса сам пушит в ветки
> `opencode/*` и открывает PR; мерж по-прежнему человек.

- **Зависимость работ**: новая разработка, опирающаяся на неслитую ветку, — на паузе
  до мержа зависимости. Независимые работы — параллельные ветки и PR.
- **Сопровождение PR (обязанность агента)**: с момента пуша ветки и до мержа/закрытия
  агент ведёт PR сам: поллить проверки (`gh pr view --json statusCheckRollup`), красные —
  разбирать по сценарию скилла `gh-fix-ci`, каждое ревью-замечание триажировать
  (коммит или аргумент в комментарии), молча не бросать. Пуш и мерж — владелец.
- **Перед каждым коммитом**: прогнать доступные проверки, посмотреть `git diff`
  (без секретов, PII, мусора); один коммит = один логический шаг.
- **Тесты обязательны**: изменение без тестов соответствующего слоя не считается
  законченным. Для шагов этого курса «тестом» является проверяемый след в GitHub:
  прогон Actions, ответ агента в issue, коммиты в PR, артефакт отчёта.
- `git clone`/`fetch`/`status`/`diff`/`log` (чтение) — можно всегда.
- **Публичная гигиена**: в коммитах, PR, коде и product-документации — без формулировок
  «в стиле ИИ» и без ссылок на `AGENTS.md`, `.agents` (внутренняя инфраструктура).
  Исключение — учебные planning-доки курса (`input/`, эта память, разделы README про
  воркфлоу по финальному шагу).
- **Формат коммитов — Conventional Commits** (`feat:`, `fix:`, `docs:`, `ci:`,
  `refactor:`, `test:`, `chore:`): нужно для release-please, который продолжает работать
  с перенесённым кодом.
- `hexlet-check.yml` — не менять (удаление/правка ломает автотесты курса).
- Дополнительные workflow (`opencode*.yml`, `e2e.yml`, `release-please.yml`, …) —
  только по явному запросу пользователя/плану шага курса.
- **Анти-петля**: агентские воркфлоу не должны срабатывать на комментарии ботов и
  собственного GitHub App (фильтр автора + узкая команда через `mentions`); каждый
  новый интерактивный воркфлоу проверять на этот риск. **Операционный критерий**:
  после ответа агента нет нового прогона того же воркфлоу на тот же issue/PR в
  течение 2 минут; доказательство — список прогонов (`gh run list`), а не чтение `if:`.
  Триаж-воркфлоу дополнительно guard'ит: только `issues`, не PR (`!issue.pull_request`)
  и только авторы `user.type == 'User'`.
- **Откат при петле**: обнаружить → попросить пользователя disable workflow в
  Actions → исправить условие → re-enable → повторный тест анти-петли; случай —
  в `mem/learnings.md`.
- **След = ссылка.** Чекбокс `[x]` в `.agents/tasks.md` ставится только с URL
  прогона/issue/PR/комментария или SHA; «должно работать» не считается.
- **Задача закрыта только после мержа в `main`.** `[x]` ставится, когда PR задачи
  слит в `main` И после мержа проект не упал (прогоны CI/автотестов на `main`
  зелёные, «след» шага виден в GitHub); до мержа задача висит `[~]`, даже если
  код готов и PR открыт. Правило нужно, чтобы контекст сессии можно было
  очистить и вернуться к реестру с любой следующей задачей/разделом без
  скрытых «почти готово».

## Память сессии

- **Журнал «Что сделано»** — `.agents/context.md`: «дата + факт + SHA» (1–2 строки).
- **Индекс фактов** — `.agents/mem/MEMORY.md`: 1 строка на запись, категории
  `user`/`feedback`/`project`/`reference`; детали — топиками рядом.
- **Извлечённые уроки** — `.agents/mem/learnings.md`: append-only, только в конец;
  обязательный ритуал конца сессии.
- **Коррекции пользователя** записывать **в моменте** (append-only),
  формат `YYYY-MM-DD | правило | источник`.
- **При старте задачи** — читать `MEMORY.md` и актуальные топики; в конце — чек-лист
  закрытия: обновить `context.md`, `MEMORY.md`, `mem/learnings.md`, `.agents/tasks.md`,
  показать список обновлённого.

## Принципы работы

- **Верифицируй работу, а не декларируй.** После правки — фактический результат
  проверок (вывод/exit-code/ссылка на прогон), а не «сделано».
- **Пойми последствия до правки (impact analysis).** Найди все затронутые места (grep);
  неясно — сначала исследование.
- **Ревью диффа перед сдачей.** Ветки с логикой (>3 файлов) — свежим контекстом.
- **Исправляй причину, а не следствие.** Не подавляй исключения, не ставь таймауты наугад.
- **Комментируй причины, а не факты** (why-comments).
- **Игнорируй чужие изменения.** Правки, которые не делал, считай осознанными.
- **Переиспользуй, не дублируй.**
- **Чекпоинты при многошаговых правках:** фиксация → проверка → зелёный (коммит) /
  красный (откат `git restore`).

## Специфика курса (шаги 2–6)

- Агент в GitHub Actions читает **этот же AGENTS.md** — команды сборки/тестов/линтера
  должны быть в нём актуальны после переноса кода (шаг 1).
- Интерактивный воркфлоу: события `issue_comment` и `pull_request_review_comment`,
  оба с `types: [created]`; права `id-token: write` + `contents: read` (checkout без
  read падает; «минимальные» = без write кроме id-token); `actions/checkout` с
  `persist-credentials: false`; работа — по команде (`/opencode`, `/oc`, набор —
  параметром `mentions`); `opencode*.yml` создаются на своих шагах 2–5, на шаге 1
  не переносятся (воркфлоу активен с момента мержа в main).
- Автотриаж (`issues`), schedule и `workflow_dispatch` — **обязателен `prompt`**
  в воркфлоу (комментария нет). Авторевью (`pull_request`) — prompt задаёт критерии,
  `use_github_token: true` для замечаний от имени раннера.
- У экшена opencode **нет параметра `timeout`** — таймаут задаётся job-level
  `timeout-minutes`; `concurrency` — в каждом агентском воркфлоу; actions — пинить
  на актуальный SHA (пины 386 могли устареть). Runbook 386
  (`github-integration.md`) — справочник намерений, не фактов: утверждения о
  шаблонах сверять с самими YAML.
- Расписание: `schedule` + `workflow_dispatch` рядом, cron в UTC, не чаще раза в сутки;
  права на запись (`contents: write`, `pull-requests: write`, `issues: write`) — только там,
  где агент сам создаёт артефакты; результат — артефакт прогона и/или issue.
- Публичный репозиторий: решение по `share` принимать осознанно и записать; круг
  вызывающих агента ограничивать условием в воркфлоу.
- Модель — под задачу (`model`, `variant`, `agent`); свести в таблицу README.
